Inference is where your fine-tuned models live once they're trained: deployed on Overmind's serving infrastructure, callable through an OpenAI-compatible API, and monitored for traffic, throughput, and latency. There are no GPUs to rent and no serving stack to operate. A model that finishes [training](/models/training) is brought online for you, and switching your agent to it is a one-line change of base URL and model name.

## Deployment lifecycle

Deployment starts automatically when a training run succeeds. A model moves through **Queued → Deploying → Warming → Ready**, and only Ready models accept traffic. Idle models cost you nothing to keep around and wake quickly when called again.

Removing a model is a **delete**, and it is irreversible. The weights go with it, which is why the console keeps it behind a confirmation and why downloading the weights first is worth considering. A failed deployment can be retried from the console without retraining anything.

## The models table

The Inference page lists every deployed model with its base model, the agent it was trained for, the training job it came from, its copyable model reference, current status, and live usage: requests, tokens, throughput in tokens per second, latency, and last activity.

Opening a model shows its full picture:

- **Lineage**: base model, agent, and training job, each linked. Any served model traces back to the exact dataset commit and eval scores that produced it.
- **Metrics**: request activity, throughput, and latency over time, with adjustable granularity.
- **Weights**: the final trained weights, downloadable, so you can run the model anywhere.

<Note>
Latency here measures model inference time only. Queueing, network, and cold starts are excluded, and requests that hit a cold model are tracked separately and left out of the warm averages. The numbers describe steady-state behaviour without blending in wake-up time.
</Note>

## Calling your model

The API is OpenAI-compatible and lives at `https://api.overmindlab.ai/api/v1`, authenticated with the same `ovr_...` API key you use for tracing. Any OpenAI SDK works. Point it at the base URL and use your model's reference (shaped like `ft-<hash>-<base>`, copyable from the models table or the training job page) as the model name.

<CodeGroup>

```python Python
from openai import OpenAI

client = OpenAI(
    base_url="https://api.overmindlab.ai/api/v1",
    api_key="ovr_your_key_here",
)

response = client.chat.completions.create(
    model="ft-abc123-qwen3-7b",
    messages=[{"role": "user", "content": "Classify this ticket: ..."}],
    stream=True,
)
for chunk in response:
    print(chunk.choices[0].delta.content or "", end="")
```

```ts TypeScript
import OpenAI from "openai";

const client = new OpenAI({
  baseURL: "https://api.overmindlab.ai/api/v1",
  apiKey: process.env.OVERMIND_API_KEY,
});

const response = await client.chat.completions.create({
  model: "ft-abc123-qwen3-7b",
  messages: [{ role: "user", content: "Classify this ticket: ..." }],
});
console.log(response.choices[0].message.content);
```

```bash curl
curl https://api.overmindlab.ai/api/v1/chat/completions \
  -H "Authorization: Bearer ovr_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "ft-abc123-qwen3-7b",
    "messages": [{"role": "user", "content": "Classify this ticket: ..."}]
  }'
```

</CodeGroup>

### Endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/v1/chat/completions` | Generate a completion (streaming via `stream: true`) |
| `GET` | `/api/v1/models` | List available models; filter with `?status=` (`ready` by default, or `deploying`, `warming`, `all`, …) |
| `GET` | `/api/v1/models/{model_id}` | One model's status and metadata |
| `DELETE` | `/api/v1/models/{model_id}` | Remove a deployed fine-tuned model |

Chat completions support the parameters you'd expect: `messages`, `stream`, `temperature`, `max_tokens`, `top_p`, `frequency_penalty`, and `presence_penalty`.

Frontier models are callable through the same API alongside your fine-tunes, from the same catalogue used for eval judging and run variants. Comparing your model against a frontier one is a change of the `model` field, not a second integration. `GET /api/v1/models` is the live source of truth for what you can call.

### Errors worth handling

| Code | Meaning | What to do |
| --- | --- | --- |
| `404` | Model not found, or not in this project | Check the model reference and the key's project |
| `503` | Model not ready, still deploying or warming | Retry shortly; poll `GET /models/{id}` for status |
| `502` | Transient backend error | Retry with backoff |
| `409` | Deletion already in progress | Nothing, it's already being removed |

## Closing the loop

Point your traced application at a deployed model and its calls flow back into [Observability](/core/observability) like any other provider's, with tokens, latency, and live eval scores included. A model switch is therefore measurable in production with the same evaluators that justified it offline. The [training benchmark](/models/training#the-benchmark-your-fine-tune-vs-your-production-model) said it should win, eval runs can pin it as a variant to keep checking, and live trace scores confirm it against real traffic.

For the switch itself, the **Model PR** from the training job edits your repository to point the agent at the new model and opens the pull request. It's the last step of the data-to-deployed-model loop, and like every other step on the platform, it ends in a review, not an automatic change.
