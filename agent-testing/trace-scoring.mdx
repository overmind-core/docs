---
title: Live scores
description: What the scores on a production trace mean, where to read them, and how to query their history.
---

Every span that reaches Overmind is scored against the capability's [eval criteria](/agent-testing/eval) as it arrives; you don't schedule anything. Once a trace's spans are scored, its root span also gets a **trajectory** score for the whole run.

## Span scores

A span is scored by the enabled [matrix rows](/agent-testing/eval#the-eval-matrix) that match it and by the [expectations](/agent-testing/eval#expectations-in-code) declared on it. Each produces a metric:

| Field | Meaning |
| --- | --- |
| `expectation` | The criterion |
| `score` | 0 to 1; missing when the row skipped the span or could not score it |
| `verdict` | `yes`, `partial` or `no` for expectations |
| `reason` | Why, for scores below 0.75 and for checks that explain themselves |
| `error` | Why the row could not score the span |

The span score is the mean of the scored metrics. A score below 0.75 comes with a reason; below 0.5 fails.

Expectations are judged against the span's **intent**: the `intent` declared on it or an ancestor, otherwise the request at the root of the trace, otherwise the capability's description. Declare `intent=` on the entry point when the request alone does not say what the user wanted.

A span keeps its score: sending it again unchanged does not re-score it, and a span whose content changed is scored again.

```json
{
  "eval_attributes": {
    "intent": "Where is order 4417?",
    "score": 0.75,
    "metrics": {
      "Correctness": {"type": "llm", "expectation": "The reply states the order's current status.", "score": 0.5, "verdict": "partial", "reason": "Names the order but not its status."},
      "output_is_valid_json": {"type": "deterministic", "score": 1.0}
    }
  }
}
```

## Trajectory scores

A single-span trace gets only `outcome`. A multi-span trace gets:

| Metric | Score |
| --- | --- |
| `outcome` | The mean span score over the spans that answer for a capability: the root and each capability's topmost span. This is the trajectory score. |
| `weakest_step` | The lowest-scoring non-root span; the reason names it. |
| `efficiency` | 1 minus the share of repeated tool calls (same tool and input) and errors never recovered. The reason adds tokens, cost and seconds. |
| `path_judge` | Whether each step moves toward the intent, with no unnecessary or out-of-order step and sensible recovery from errors. |
| `reference` | Only when the entry point declares `reference_trajectory`: how closely the tools called match it, and whether they ran in order. |

A trajectory `passed` when its score is at least 0.5 and no span failed. The trace list shows the trajectory score when the root has one, otherwise the root's span score; the span panel lists every metric with its verdict and reason.

## Score history

`eval_attributes` holds the latest result. Every span score, trajectory score and evaluation-run row score is also appended to the history:

```bash
curl -H "X-Api-Key: $OVERMIND_API_KEY" \
  "https://api.overmindlab.ai/api/eval-scores/?project={id}&trace_id={trace_id}"
curl -H "X-Api-Key: $OVERMIND_API_KEY" \
  "https://api.overmindlab.ai/api/eval-scores/?source_type=trajectory&source_id={trace_id}"
```

Each entry has `source_type` (`span`, `trajectory` or `dataset_row`), `source_id`, `run`, `score`, `metrics` and `created_at`. Filters: `project`, `source_type`, `source_id`, `source_id__in`, `run`, `trace_id`.

Over MCP, `query_traces` returns each trace's score, `query_failures` returns recent traces of a capability with a failing span or trajectory and the reasons, and `inspect_capability_health` aggregates scores per metric with coverage against the previous window.

[Signals](/agent-testing/signals) watch these scores for drops and repeated failures.
