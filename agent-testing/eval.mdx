Eval is where you define what "good" means for a capability and measure it. One set of criteria, the capability's **active eval set**, is used everywhere:

| Where | What gets scored |
| --- | --- |
| [Live scores](/agent-testing/trace-scoring) | Every production span as it arrives |
| [Evaluation runs](#run-an-evaluation) | A dataset, replayed through one or more models |
| [`overmind backtest`](/platform/cli#overmind-backtest) | Stored model calls, replayed through candidate models |
| [Optimiser](/agent-testing/optimisers) | Your agent before and after each candidate change |
| [Training](/models/training#the-benchmark) | The model before and after training |

## Set up evals

<Steps>
  <Step title="Run /overmind setup">
    The scan writes your capabilities to `overmind.toml`, including the [checks](#checks-in-the-toml) the code's contracts allow. `overmind sync` creates the capabilities and a **Default** eval set for each.
  </Step>
  <Step title="Declare expectations in code">
    Setup decorates the functions your capability card names and puts the judge criteria on them as [`expectations`](#expectations-in-code). Add or edit them like any other code.
  </Step>
  <Step title="Sync again">
    Run `overmind sync` after the decorators are in place. Sync reads the expectations from your code and adds them to the Default set, so evaluation runs, backtests, the optimiser and training judge the same criteria as live scoring.
  </Step>
  <Step title="Check the set">
    Open the capability's **Eval matrix** tab, or **Evaluations → Eval sets**, to see the rows the Default set holds.
  </Step>
</Steps>

Repeat the last two steps whenever you change expectations or checks. An expectation you delete from the code leaves the set at the next sync.

## The eval matrix

A matrix row is one criterion. Every row has a `name`, a `type`, a `source`, an optional `capability` (blank applies it to every capability in the project), an optional `span_type` and `span_name` that narrow where it applies, and an `enabled` switch. Rows are created and deleted, never edited: to change one, delete it and create its replacement.

<Tabs>
  <Tab title="Expectation (llm)">
    The source is one sentence the output must meet, for example "The reply quotes the order id and its status." A judge answers `yes`, `partial` or `no` (scores 1, 0.5 and 0) against the span's intent, input, output and any reference. A score below 0.75 comes with a written reason; below 0.5 fails.

    Write each expectation as one concrete, checkable claim about the output. Keep data values and secrets out of it.
  </Tab>
  <Tab title="Python check (deterministic)">
    The source is a Python function:

    ```python
    def evaluate(span):
        if not span.output:
            return None
        return "order" in span.output, "the reply names the order"
    ```

    Return a score in [0, 1], a bool, a `(bool, reason)` tuple, or `None` to skip the span. The span exposes `input`, `output`, `expected`, `tool`, `status`, `duration_s`, `usage` and `attributes`, plus its `parent`, `children` and `siblings`. `json` and `re` are available; `import` is not.
  </Tab>
</Tabs>

**Where a row applies.** On production traces, a row scores the spans it matches: the right capability, and the `span_type` and `span_name` when they are set. A row with neither applies to the capability's answer, the root span or the topmost span of each capability. Over a dataset, each row stands for the capability's answer, so it takes every row whose `span_type` is blank or `llm_call`, whatever its `span_name`. Rows scoped to `tool_call`, `retrieval` or `workflow` spans score production traces only.

### Expectations in code

Put judge criteria on the function whose output they describe:

```python
import overmind

@overmind.entry_point(
    capability_id="<capability-uuid>",
    intent="Answer a support ticket",
    expectations=[
        "The reply quotes the order id and its status.",
        "The reply is at most two sentences.",
    ],
)
def answer(ticket: str) -> str:
    ...
```

Every traced span is judged against its own expectations. `overmind sync` also copies the expectations on entry points, workflows and plain `observe` decorators into the capability's Default set, scoped to that function, so dataset runs use them too. Expectations on `tool` and `retrieval` decorators describe a step and score production traces only. `overmind.expect("constraint", "...")` adds an expectation at runtime, for the current trace only. See the [Python SDK](/tracing/sdk-python#runtime-expectations).

### Checks in the toml

A capability's `eval_matrix` in `overmind.toml` holds deterministic checks from the catalog below. Name the check, set its parameters, and optionally scope it:

```toml
[[capabilities.support-agent.eval_matrix]]
name = "Reply carries ticket keys"
type = "deterministic"
check = "json_required_keys"
params = { REQUIRED_KEYS = ["ticket_id", "status"] }
span_name = "SupportAgent.run"
```

`overmind sync` turns each entry into a row in the Default set. Sync refuses the whole file, naming the entry, when `check` is not in the catalog or `params` names a parameter the check does not have. Judge criteria never go in the toml; declare them in code.

| Check | Passes when | Params |
| --- | --- | --- |
| `output_is_valid_json` | The output parses as JSON | |
| `tool_selection` | The tools called match the span's `reference_trajectory` (F1) | |
| `exact_match` | The output equals the reference | `REFERENCE`, `CASE_INSENSITIVE` |
| `contains` | The output contains a string | `NEEDLE`, `CASE_INSENSITIVE` |
| `regex` | The output matches, or does not match, a pattern | `PATTERN`, `MUST_MATCH` |
| `goal_state_match` | Every marker appears in the output | `GOAL_MARKERS` |
| `json_required_keys` | The JSON output has every key | `REQUIRED_KEYS` |
| `schema_field_conformance` | JSON fields follow their rules (`type`, `enum`, `min`, `max`, `pattern`, `nullable`) | `FIELDS` |
| `tool_args_match` | The expected tool calls are made with matching arguments | `EXPECTED_CALLS`, `MODE` (`exact`, `subset`, `superset`) |
| `llm_call_budget` | The span and its children make at most N model calls | `MAX_LLM_CALLS` |
| `latency_budget` | A model call takes at most N seconds | `MAX_SECONDS` |
| `cost_budget` | A model call costs at most N | `MAX_COST` |

Every project also gets each of these as a project-wide row. `output_is_valid_json` and `tool_selection` start enabled; the rest start disabled and skip every span until configured. Checks that read tools, timing or cost skip dataset rows, which carry only the input, output and reference.

### Rows from the Console or MCP

**Evaluations → Eval matrix**, or a capability's **Eval matrix** tab, lists every row with its scope. **New row** creates an expectation or a Python check, with examples to start from. Over MCP, use `create_eval_matrix_row` and `delete_eval_matrix_row`; over REST, `POST` and `DELETE` on `/api/eval-matrix/`.

## Eval sets

An eval set is a named list of matrix rows, optionally tied to a capability. One set per capability is **active**: evaluation runs, the optimiser and training use it unless you pick another. `overmind sync` keeps a **Default** set for every capability, holding its code expectations, its toml checks and the enabled project checks that fit its spans; the Default set becomes active when the capability has none.

To grade with a different selection, create a set from row ids or names and activate it:

- MCP: `create_eval_set` with `name`, `capability`, `rows` and `activate`.
- REST: `POST /api/eval-sets/` with `project`, `name`, `capability` and `rows`, then `POST /api/eval-sets/{id}/activate/`.

A set without a capability can be chosen for a run but cannot be activated. **Evaluations → Eval sets** lists every set.

## Run an evaluation

A run scores one **target** over one dataset version. Creating a run with several targets creates one run per target in a shared **group**; one target can be the **baseline** the others are compared with.

| Target `mode` | Output scored |
| --- | --- |
| `recorded` | The dataset's own outputs |
| `generate` | Each row replayed through `model_name` (a catalogue model or registered endpoint) or `model_ref` (one of your trained models) |

The dataset must have the eval intent; see [Datasets](/core/datasets#contracts). A run grades with the eval set you pass, else the capability's active set. Its rows are copied into the run when it starts, so later edits never change what a run measured.

<Tabs>
  <Tab title="From a coding agent (MCP)">
    1. Call `check_evaluation_readiness` with the dataset, the targets and an optional `eval_set` and `judge_model`. It reports whether the run can start, the rows it will grade, estimated cost and context warnings.
    2. Call `run_evaluation` with a name, the dataset, the targets and the same choices. It returns the group and one run per target.
    3. Poll each run with `get_job(kind="eval_run", id=...)`, then read `overmind://eval-runs/{id}`.
    4. Call `compare_evaluations` with a candidate run.

    The native prompts `prepare-evaluation` and `evaluate-change` walk an agent through the same steps.
  </Tab>
  <Tab title="REST">
    ```bash
    # A recorded baseline and two candidates over one dataset version
    curl -X POST -H "X-Api-Key: $OVERMIND_API_KEY" -H "Content-Type: application/json" \
      -d '{
        "project": "<project-uuid>",
        "name": "Triage backtest",
        "dataset": "<dataset-uuid>",
        "eval_set": "<eval-set-uuid>",
        "targets": [
          {"label": "production", "mode": "recorded", "is_baseline": true},
          {"label": "gpt-5-mini", "mode": "generate", "model_name": "openai/gpt-5-mini"},
          {"label": "trained", "mode": "generate", "model_ref": "<model-ref-uuid>"}
        ]
      }' \
      "https://api.overmindlab.ai/api/eval-runs/"

    curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/eval-runs/?group=<group-uuid>"
    curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/eval-runs/{id}/comparison/"
    curl -X POST -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/eval-runs/{id}/run/"     # re-launch
    curl -X POST -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/eval-runs/{id}/cancel/"
    curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/eval-run-rows/?run={id}"
    ```

    Creation returns `{group, runs}`. List filters on `/api/eval-runs/`: `project`, `status`, `mode`, `dataset`, `group`, `is_baseline`, `capability`, `created_after`, `created_before`.
  </Tab>
  <Tab title="CLI">
    `overmind backtest` builds a dataset from the capability's stored model calls, runs the recorded outputs as the baseline and each `--model` as a candidate under the active eval set, and exits 1 when a candidate regresses. See the [CLI](/platform/cli#overmind-backtest).
  </Tab>
</Tabs>

The Console lists runs and their results; it does not start standalone runs. An eval dataset's cell offers **Run the optimiser** and **Use in a training job**.

For recorded conversations, a generate target can set `params.generation_strategy` to `per_assistant_turn`: the model answers each recorded assistant turn with the history before it as context. Tool calls are scored as decisions without running the tools.

A run's `status` moves `pending` → `running` → `completed`, or ends `failed` or `cancelled`. A re-launched run re-scores from the same inputs. A row whose generation hit its output-token limit is marked degraded and left out of the trusted score.

### Judge model

`judge_model` picks the model that writes reasons for low expectation scores; blank uses the default. It is fixed for the run. Training's `eval_judge_model` sets it for one job.

Readiness and training setup estimate whether each target and the judge fit their context window. Warnings are advisory: undersized options stay selectable, and Start opens a short summary with **Start anyway**. `POST /api/eval-runs/context-check/` returns the same estimates without starting anything.

### Read the results

A run's summary holds the headline `score` (mean row score, 0–1), each metric's `mean`, `n`, `failed` and `errors`, the row counts `rows`, `scored`, `errored` and `degraded`, and `trust`. When references are labels, `class_metrics` adds per-class precision, recall, F1 and a confusion matrix.

The run page shows the target, dataset version, rows graded and judge. **Results** lists every row: open one for each metric's score, verdict and reason beside the input, reference and output.

### Compare with the baseline

`GET /api/eval-runs/{id}/comparison/`, MCP `compare_evaluations`, and the run page's **Baseline comparison** tab compare a run with its group's baseline. Only rows both runs scored are paired. The comparison reports overall and per-metric baseline, candidate, delta and status, plus `paired`, `wins`, `losses` and `ties`. A delta within half a percentage point is `unchanged`; otherwise `improved` or `regressed`. A metric only one run has is `added` or `removed`. Trust warnings appear when either run has errored or degraded rows.

## Use evals in other workflows

Each workflow grades with the capability's active eval set unless you choose another, and keeps the same rows for its whole run.

- **Backtest and model comparison.** `overmind backtest` and the optimiser's **Compare models** mode replay the same data through each candidate model and compare every candidate with the baseline. See [Optimisers](/agent-testing/optimisers#modes).
- **Optimiser.** Each candidate change is scored as an evaluation run against your agent's baseline. See [Optimisers](/agent-testing/optimisers).
- **Training.** Training setup picks the eval dataset, eval set and judge, and scores the model before and after training. See [Training](/models/training#the-benchmark).
- **Signals.** Subscriptions watch live scores for drops and repeated failures. See [Signals](/agent-testing/signals).
