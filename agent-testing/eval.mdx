Eval is where you define what "good" means for an agent and measure it — in batch runs that compare models and prompts side by side, and continuously on production traces as they arrive. The same evaluators serve both, so an improvement measured offline is directly comparable to live scores.

The **Evaluations** area of the console has three surfaces: **Runs**, **Eval Sets**, and the **Eval Library**.

## Evaluators

An evaluator is one reusable, versioned scorer — editing one creates a new version, so past runs keep meaning what they meant. Six kinds exist:

<AccordionGroup>
  <Accordion title="LLM judge (llm_judge)">
    A model grades the response against a rubric you write in plain language. The rubric is compiled into a checklist of atomic, weighted questions; items can be **gates** that force a fail regardless of the rest of the score. Judges return reasoning and per-item sub-scores. For higher-stakes metrics, configure a **panel of judges** instead of a single model. Long traces are handled by a summarising cascade, and judge responses are cached content-addressed, so re-scoring identical inputs is free.
  </Accordion>
  <Accordion title="Deterministic (deterministic)">
    A fixed rule, no model involved. Available checks: `exact_match`, `contains`, `regex`, `json_schema_valid`, `tool_selection` (precision/recall/F1 over called tools), `tool_args_match`, `no_redundant_calls`, `subgoal_progress`, `goal_state_match`, `latency`, `cost`, `turn_count`, and `card_constraints`. Fast, free, unambiguous — use these wherever the question has a mechanical answer.
  </Accordion>
  <Accordion title="Trajectory (trajectory)">
    Judges the path the agent took, not just the output. Two modes: **match** compares the tool-call sequence against a reference with `strict`, `unordered`, `subset`, `superset`, or `subsequence` semantics (with per-tool argument-match overrides), or **judge** hands the trajectory to an LLM.
  </Accordion>
  <Accordion title="Agentic (agentic)">
    An LLM judge built for long, multi-step agent runs where there is a lot of trajectory to read and summarise before scoring.
  </Accordion>
  <Accordion title="Statistical (statistical)">
    Scores a whole dataset at once rather than one example at a time: `accuracy`, `precision`, `recall`, `f1` (macro/micro/weighted), `exact_match`, `bleu`, `rouge_l`, `embedding_cosine`, `chrf`, and `duplicate_rate`, with configurable prediction normalisation (`strip`, `first_word`, `last_word`, `first_line`, `last_line`, or a custom `regex:` extractor).
  </Accordion>
  <Accordion title="Decision graph (dag)">
    Evaluates structured decision logic — whether the agent's choices followed the expected branching — composing the other evaluator families as nodes.
  </Accordion>
</AccordionGroup>

Every evaluator declares a **scope** (`final_output`, `turn`, `step`, `trajectory`, `sample`, or `dataset`), a **score type** (numeric, categorical, or boolean) with a **pass threshold**, and an **evidence requirement** (model output, trajectory, or a reference answer). If a run can't supply the required evidence, the evaluator abstains or is marked not-applicable instead of producing a meaningless number.

### Authoring

Author from the Eval Library by hand, or describe what you want to test and let Overmind generate the evaluator. The generated prompt template references the agent's output as `{{output.<path>}}` and dataset fields as `{{reference.<path>}}`, and everything stays editable before saving. Repository scans also author a starter set per agent automatically.

## Eval sets

An eval set is a named group of an agent's evaluators — the working definition of "good" for that agent. Each member carries a **role**:

- **Generative** members score outputs produced during eval runs and experiments.
- **Trace scoring** members run on live production traces as they arrive (with a configurable sampling rate), writing scores into [Observability](/core/observability#scores-on-arrival).

The same evaluator can hold both roles. One set per agent is **active** — it's what optimisation runs and benchmarks default to.

## Eval runs

An eval run is a controlled experiment: **one data source × N variants × M evaluators.**

- **Data source** — a dataset (the exact commit is recorded, so the run stays reproducible as the dataset evolves) or a trace filter drawing directly from captured traffic. `max_items` caps how many rows are drawn.
- **Variants** — the columns of the experiment. A variant either **generates** fresh outputs by re-running a model over each datapoint, or grades **existing** traces as-is. Each pins a model (a catalogue model, a registered endpoint, or one of your trained models) and optionally a prompt version; one variant is the **baseline** that every other is measured against.
- **Evaluators** — attached as frozen snapshots at creation, so later library edits can't change what a completed run measured.

```bash
# Create, launch, follow, and compare a run
curl -X POST -H "X-Api-Key: $OVERMIND_API_KEY" -H "Content-Type: application/json" \
  -d '{
    "agent": "<agent-uuid>",
    "data_source": "dataset",
    "dataset": "<dataset-uuid>",
    "variants": [
      {"mode": "existing", "is_baseline": true},
      {"mode": "generate", "model_name": "<model-ref>"}
    ],
    "eval_set": "<eval-set-uuid>"
  }' \
  "https://api.overmindlab.ai/api/eval-runs/"

curl -X POST -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/eval-runs/{id}/run/"
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/eval-runs/{id}/comparison/"
```

Execution fans out server-side: sample preparation (generation), then one scoring task per sample × evaluator, then aggregation into the run summary. Runs move through pending → running → completed (or failed/cancelled) and can be cancelled mid-flight.

Two details in the scoring model are worth understanding:

- **Outcomes are typed.** Every score is `scored`, `abstained`, `not_applicable`, `skipped`, or `error` — and only `scored` results feed averages and pass rates.
- **Samples can be degraded.** Each trace is normalised into a canonical transcript before scoring; if it can't be faithfully reconstructed, the sample is marked degraded and excluded from aggregates rather than silently polluting them. Failure scores also carry a role — root cause vs. propagated — so one upstream failure doesn't read as five independent ones.

Completed runs can be shared read-only via tokenised share links, and scores accumulate into a per-agent history that powers the trend charts on the agent page.

## Calibrating judges

Samples accept **annotations** — human labels with an optional note — giving you ground truth to compare judge behaviour against. When a judge and your annotations disagree consistently, tighten the rubric; the checklist compilation makes it easy to see which specific criterion is drifting.

## Getting started sensibly

Begin with three to five metrics: a deterministic check or two for your output contract (`json_schema_valid`, `tool_selection`), one judged metric for the quality dimension you care about, and a reference-based check if you have labelled data. Run them against a small real dataset, read the per-example reasoning, fix the rubric where the judge misunderstood you — then scale up.
