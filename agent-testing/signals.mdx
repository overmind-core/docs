---
title: Signals
description: Patterns over recent production spans that a project subscribes to, and the in-app events they raise.
---

A signal is a pattern Overmind checks across recent spans: falling scores, a tool that keeps erroring, a user repeating themselves, a cost spike. You subscribe a project, or one capability, to the signals you care about. Each finding becomes a **signal event** in the Console. Events are in-app only.

No signal is on by default. Every five minutes Overmind runs each project's enabled subscriptions over the spans received in the last day, grouped by conversation (or by trace outside a conversation). A finding is recorded at most once per subscription, group and day.

## The catalog

| Signal | Raised when | Params (default) |
| --- | --- | --- |
| `low_scores` | The last scored spans all fall below the failing score | `run` (5) |
| `score_drop` | The mean of the most recent scores falls against the earlier mean | `window` (5), `drop` (0.2) |
| `repeated_failure` | One expectation fails repeatedly | `times` (3) |
| `hidden_failure` | A step fails under a root answer that passes | |
| `unscorable` | Evaluated spans end without a score | `rate` (0.5) |
| `errors` | Spans end with an error status | |
| `tool_failure` | A tool errors on a large share of its calls | `min_calls` (3), `rate` (0.5) |
| `retry_storm` | One call is retried repeatedly under the same parent after an error | `times` (3) |
| `swallowed_error` | A span errors inside a trace whose root finishes ok | |
| `abandoned` | A trace has no root span long after its first span arrived | `minutes` (10) |
| `loop` | A tool is called repeatedly with the same input in one trace | `times` (3) |
| `runaway_trace` | A trace has many times the usual number of spans | `factor` (3) |
| `plan_drift` | Steps are judged as not working toward the intent | |
| `abandoned_session` | A conversation goes idle after a failing or errored span | `minutes` (30) |
| `repeated_input` | The user repeats their previous message | |
| `frustration` | The user corrects the agent | |
| `context_overflow` | Root scores fall in the second half of a long conversation | `turns` (10), `drop` (0.2) |
| `slow_llm` | LLM calls take many times the usual latency | `factor` (3) |
| `token_spike` | LLM calls use many times the usual tokens | `factor` (3) |
| `cost_spike` | LLM calls cost many times the usual amount | `factor` (3) |
| `model_change` | Scores fall after the model changes | `drop` (0.2) |
| `leak` | Outputs contain an API key, an email address or a card number | |
| `refusal` | Outputs refuse the task | |
| `broken_json` | Outputs open as JSON but do not parse | |
| `hallucinated_tool` | An LLM requests a tool that never runs in the trace | |

The score-based signals read the [live scores](/agent-testing/trace-scoring), so they only find what your [eval criteria](/agent-testing/eval#set-up-evals) measure. `plan_drift` judges each scored step once, which costs credits.

A good first set: `low_scores` and `repeated_failure` to catch criteria that keep failing, `tool_failure` and `errors` for broken steps, and `score_drop` after a deploy. When `repeated_failure` names an expectation, open a failing trace and decide whether the agent or the expectation needs to change.

## In the Console

**Signals** in the sidebar carries a count of unseen events. The **Events** view lists each event's signal, message, capability, trace and time, filters by signal type or unseen events, and marks all as seen. The **Subscriptions** view lists the catalog: switch a signal on for the project and edit its params.

## Over the API

A subscription has a `project`, an optional `capability` (blank covers every capability), a `signal_type`, `enabled` and a `config` of param overrides. Each override must name a param of that signal and keep its type; numbers must be positive. One subscription exists per project, capability and signal type; to change its scope, create a new one.

```bash
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/signal-subscriptions/catalog/"

curl -X POST -H "X-Api-Key: $OVERMIND_API_KEY" -H "Content-Type: application/json" \
  -d '{"project": "<project-uuid>", "signal_type": "tool_failure", "config": {"rate": 0.3}}' \
  "https://api.overmindlab.ai/api/signal-subscriptions/"

curl -H "X-Api-Key: $OVERMIND_API_KEY" \
  "https://api.overmindlab.ai/api/signal-events/?project=<project-uuid>&unseen=true"

curl -X POST -H "X-Api-Key: $OVERMIND_API_KEY" -H "Content-Type: application/json" \
  -d '{"project": "<project-uuid>"}' \
  "https://api.overmindlab.ai/api/signal-events/mark-seen/"
```

An event carries `signal_type`, `message`, `capability`, `conversation`, `trace_id`, `details`, `occurred_at` and `seen_at`. Event filters: `project`, `unseen`, `signal_type`, `capability`, `trace_id`, `conversation`. `mark-seen` marks the listed `ids`, or every unseen event of the project, and returns the number `updated`.

Over MCP, `list_signals` returns the catalog with the project's subscriptions and its unseen event count, `set_signal_subscription` enables, disables or configures one signal for the project or one capability, and `overmind://signal-events` lists recent events.
