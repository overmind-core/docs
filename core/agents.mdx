An agent in Overmind is a record of an agent you already run, not something you build in the console. The record joins two sides: static structure read from your repository (prompts, tools, control flow, entrypoint) and runtime behaviour from telemetry (traces, token usage, live scores). Everything else on the platform hangs off it — traces are attributed to an agent, datasets can be bound to one, evaluators are scoped per agent, optimisation runs edit an agent's code, and trained models are benchmarked against an agent's production model.

## How agents get into Overmind

```flow
flow row
title: Three paths into the same agent record

B[Production telemetry] -> C : overmind.agent.* attributes
D[overmind CLI] -> C : optimisation runs
C -> E[Traces]
C -> F[Datasets]
C -> G[Eval sets]
C -> H[Optimisation runs]
C -> I[Trained models]
```

### Repository scan

Connect GitHub from **Agents → Connect a repository** (or during onboarding). You install the Overmind GitHub App on the specific repositories you choose; for a public repository, paste its URL instead — no account connection needed. Pick a branch and Overmind clones and analyses it, discovering each agent and mapping its prompt, tools, and control flow.

The scan populates the agent's **evaluation spec** — its input schema, expected output fields, tool configuration, and consistency rules — plus the split between **optimisable elements** and **fixed elements** that later bounds what the [Optimiser](/agent-testing/optimisers) may touch. It also generates a starter set of [evaluators](/agent-testing/eval) grounded in the agent's job and a **policy document** describing correct behaviour; both remain editable afterwards.

A background check compares the scanned commit against your branch head; when the branch moves on, the agent shows as out of sync and you can re-analyse.

### Telemetry

When spans arrive carrying an agent identity — `overmind.agent.id` or `overmind.agent.name`, set via the [SDK](/tracing/sdk-python#context-helpers) — Overmind attaches them to the matching agent, creating it automatically from the name if it doesn't exist yet. Prefer `overmind.agent.id` (the agent's UUID): it is a direct lookup, so renames never break attribution and telemetry can never mint a duplicate. Names are slugified into a stable identity as a fallback, so keep them constant across deploys; a drifting name mints duplicate agents. An agent discovered from code and the same agent reporting telemetry resolve to one record. In a repo with several agents, each agent stamps its own id and name at its own entry point, so spans group per agent even when they share one process.

### The CLI

[Optimisation runs](/agent-testing/optimisers) executed with the `overmind` CLI push their agent, dataset, and score artifacts to the same records.

## The agent page

Open an agent from the **Agents** list. The header carries copyable **agent id** and **project id** chips (you'll need the agent id for trace attribution), a **View traces** shortcut into its filtered Observability view, and an **Archive** action.

Four tabs:

- **Overview** — a facts bar (model, source, built-from component counts, trace coverage), the system prompt lifted from your code, a components explorer with file-level provenance, and the interactive flow graph. This is the fastest way to check that Overmind read your code correctly.
- **Dataset** — datasets attached to this agent, built from its traces or uploaded. See [Datasets](/core/datasets).
- **Eval metrics** — the agent's evaluators and eval sets, with score history. See [Eval](/agent-testing/eval).
- **Models** — the production baseline and any models trained on this agent's data, linking into [Training](/models/training) and [Inference](/models/inference).

## Trace coverage and the observability PR

The overview reports **trace coverage**: which of the agent's discovered components actually emit telemetry. Clicking it lists every untraced entrypoint and tool with file/line references, and provides a ready-made instrumentation prompt you can copy into your editor's AI assistant.

<Frame caption="Trace coverage: 0 of 3 components traced, each untraced entrypoint linked to its source location, with a copyable instrumentation prompt.">
  <img src="/images/platform/trace-coverage.png" alt="Trace coverage panel with untraced components" />
</Frame>

Alternatively, Overmind can write the missing tracing code itself and open a pull request against your branch (the **observability PR**). The PR adds SDK initialisation and span decorators, and appends an `OVERMIND_API_KEY=` placeholder to your `.env.example` so the deployment wiring is explicit. Status is tracked per repository (not started → in progress → PR open → merged).

## API

```bash
# List agents / one agent
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/agents/"
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/agents/{id}/"

# The machine-readable evaluation spec and prompt versions
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/agents/{id}/eval_spec/"
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/agents/{id}/prompts/"
```

`PATCH /api/agents/{id}/` updates mutable fields; `DELETE` soft-deletes (archives). See the [REST API](/platform/api) overview for the full surface.

## Good to know

- **Prompts are versioned.** Each scan or optimisation iteration snapshots the system prompt, tools JSON, and model as a numbered prompt version, retrievable via `/api/agents/{id}/prompts/`.
- **The baseline matters.** The agent's `model` field is what training benchmarks and optimiser baselines measure against — keep it accurate.
- **Archiving hides, it doesn't delete.** Traces, datasets, and runs underneath an archived agent remain intact.
