Overmind's observability is built on OpenTelemetry end to end. Your process exports standard OTLP spans; the platform ingests them, maps them onto its data model, ties them to a capability, and scores each arriving trace with your evaluators. This page covers the full path a span travels, with the real endpoints, headers, and attribute names the platform reads.

## Architecture

There is no collector, sidecar, or proxy between your agent and the platform. SDKs (and any vanilla OTel exporter) POST OTLP protobuf directly to the API, which writes spans to Postgres and fans out post-processing to background workers:

```flow
flow row
title: The ingestion pipeline, span by span
A[Your process | OTel SDK / Overmind SDK] -> B[POST /api/v1/traces | OTLP protobuf + API key]
B -> C[Bulk upsert | Span rows, idempotent on span_id]
C -> D[Projection | capability and session attribution]
D -> E[Trace scoring | units carved, bound to tasks, judged]
E -> F[Console | executions, traces, sessions]
```

Ingestion is synchronous up to the database write, so a `200` response means your spans are stored. Re-sending the same spans is safe: rows are upserted on the span ID, so retries and duplicate exports never create duplicate data. Trace scoring is queued the moment a root span lands and runs on its own worker queue, isolated so ingest bursts can't starve evaluation.

## The OTLP endpoint

| | |
| --- | --- |
| Endpoint | `POST https://api.overmindlab.ai/api/v1/traces` (alias: `POST /v1/traces`) |
| Protocol | OTLP/HTTP **protobuf** (`ExportTraceServiceRequest`). OTLP/JSON and gRPC are not accepted |
| Content-Type | `application/x-protobuf`; gzip-compressed bodies are supported |
| Auth | `X-Api-Key: ovr_...`, `Authorization: Bearer ovr_...`, or `Authorization: Api-Key ovr_...` |
| Response | `{"spans_ingested": N, "spans_post_processed": M}` |

The `/v1/traces` alias exists so a stock OTel HTTP exporter works with nothing but a base URL — exporters append `/v1/traces` themselves:

```bash
export OTEL_EXPORTER_OTLP_ENDPOINT="https://api.overmindlab.ai"
export OTEL_EXPORTER_OTLP_PROTOCOL="http/protobuf"
export OTEL_EXPORTER_OTLP_HEADERS="x-api-key=ovr_..."
```

The API key pins every span in the request to its project. Trace ingest is deliberately exempt from credit gating — running out of credits never drops your telemetry. A self-hosted API takes the same requests at `http://localhost:8000`.

## Getting traces in

The fastest path is the one the empty Observability page hands to your coding agent: pick the client, **Copy prompt**, paste. The prompt tells the agent to install `overmind[tracing]`, call the `get_instrumentation_plan` MCP tool for exact placements, apply them, and then verify one real trace with `verify_instrumentation` — the same loop the `/overmind ensure-tracing` command runs. See [MCP](/platform/mcp).

In a local repository, run `overmind sync` first so the Python SDK can reuse its saved project credential. Deployed processes and non-Python SDKs should receive `OVERMIND_API_KEY` through their runtime secret configuration. To instrument by hand:

        capability="Research Agent",  # display label; optional

## How spans map to the data model

A trace is not a separate record: it is the set of span rows sharing a `trace_id`, and the root span (the one with no parent) is what the trace list shows. Each stored span keeps the full OTLP payload — timing, status, resource attributes, span attributes, events, and links — plus platform fields computed at ingest: a span type, an operation name, and foreign keys to the project, capability, and conversation it belongs to.

### Span classification

Each span is typed at ingest, in priority order:

1. An explicit `overmind.span.type` attribute (`entry_point`, `workflow`, `tool_call`, `function`, `llm_call`, `retrieval` — what the SDK decorators set) always wins; `overmind.span_type` and bare `type` are accepted spellings.
2. An OpenInference `openinference.span.kind`: `llm` and `embedding` become model calls, `tool` a tool call, `retriever` and `reranker` retrieval, `chain`, `agent`, `guardrail`, and `evaluator` workflow spans.
3. `gen_ai.operation.name = "execute_tool"` or a `tool.name` attribute marks the span as a tool call.
4. A span name containing `tool`, `function_call`, `function.call`, or `execute_tool` marks it as a tool call.
5. Otherwise the span is a model call.

### Attributes the ingest pipeline reads

The pipeline understands three attribute dialects — the Overmind SDK's own keys, the OTel GenAI semantic conventions, and OpenLLMetry/Traceloop keys — checked in that priority order:

| Purpose | Attribute keys (priority order) |
| --- | --- |
| Input tokens | `genai.usage.prompt_tokens`, `genai.prompt_tokens`, `gen_ai.usage.prompt_tokens`, `gen_ai.usage.input_tokens`, `llm.usage.prompt_tokens` |
| Output tokens | `genai.usage.completion_tokens`, `genai.completion_tokens`, `gen_ai.usage.completion_tokens`, `gen_ai.usage.output_tokens`, `llm.usage.completion_tokens` |
| Cached tokens | `genai.cache_read_tokens`, `gen_ai.usage.cache_read_input_tokens`, `gen_ai.usage.cache_read_tokens` |
| Model | `genai.model`, `genai.response.model`, `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.model` |
| Cost | `genai.cost` if the client stamped it, otherwise derived from token counts and model pricing |
| Inputs / outputs | `overmind.input.data` / `overmind.output.data`, `traceloop.entity.input` / `.output`, `gen_ai.input.messages` / `gen_ai.output.messages`, indexed `gen_ai.prompt.{N}.*` / `gen_ai.completion.{N}.*` |
| Capability identity | `overmind.capability.id` (the mapping key), `overmind.capability.name` (display label) |
| Session grouping | `conversation.id` |
| Scoring unit | `overmind.unit_kind` (`run` / `turn`), `overmind.delivery` (the terminal deliverable), `overmind.behaviour.key` (a declared task), `overmind.grounded_by` (the evidence spans a deliverable rests on), `overmind.provenance` (`user`, `agent`, `environment`, `harness`) |
| Code identity | `code.namespace`, `code.function.name`, `vcs.ref.head.revision` — how a unit binds to a synced task |
| Runtime expectations | span events `overmind.eval.intent`, `overmind.eval.expectation`, `overmind.eval.checkpoint`, `overmind.eval.context`, `overmind.eval.conversation_end` |
| Project (session-auth ingest only) | `overmind.project.id` resource attribute |

Traceloop instrumentation is normalised on the way in — scope names under `@traceloop/*` are rewritten to `@overmind/*` — so OpenLLMetry-instrumented apps work without changes.

### Capability attribution

Traces attach to a [capability](/core/capabilities) through one attribute:

- **`overmind.capability.id`** — the capability's UUID, copied from its page in the Console. The only key ingest binds by; stable through renames. A span-level id wins over the resource-level one, so one process can serve several capabilities.
- **`overmind.capability.name`** — a display label shown beside raw span attributes. It never resolves a capability.

The Python SDK stamps both from one setting: `overmind.init(capability_id=...)`, or a `capability(..., id=...)` scope per request in a multi-capability process; switching capability mid-trace is a handoff that [trace scoring](/agent-testing/trace-scoring#tasks-and-bindings) scores as its own unit. A child span that carries no identity — a subprocess, say — inherits the trace's capability when the trace maps to exactly one.

An id the project does not know never creates a capability. The span lands under the **Unbound** filter instead, and binds retroactively once the id resolves (a deleted capability restored, or a backlog rebind after a sync). Sync (or create the capability) first, then copy its id into the SDK.

<Warning>
Unbound spans are stored and browsable, but they won't appear on any capability's page, won't be live-scored by its evaluators, and won't join capability-scoped datasets until they bind. A name is never enough — set `capability_id` from day one.
</Warning>

### Sessions

Stamp a shared `conversation.id` on the traces of one multi-turn exchange — `set_conversation_id("session-42")`, or `run(conversation_id=...)` — and Overmind groups them into a **session** with rolled-up trace counts, tokens, cost, timespan, and a **session score** folded from the asks the user made and which ones were delivered. The **Sessions** view in Observability lists them.

### Trace status

A trace is `live` while spans are still arriving or the root span is missing, `completed` once the root has landed, and `interrupted` when no root arrives inside the settle window (`TRACE_SETTLE_SECONDS`, default 600 s). The trace list, the trace header, and `GET /api/traces/` (`trace_status`) all carry it; a live trace keeps polling in the Console.

## Scores on arrival

When a root span lands, the platform carves the trace into **units**, binds each unit to one of the capability's **tasks** as a **task execution**, and runs the trace-scoring members of the active [eval set](/agent-testing/eval#eval-sets) against each unit. Every verdict is stored as its own row, read over `GET /api/verdicts/`; the unit's span keeps the composed markers in `feedback_score.trace_scoring`, whose `_execution.score` is the composite the Console shows in the **Score** column. Sessions get a score of their own. A trace that never sends its root is picked up by a sweep once it is `interrupted`. The full contract — carve precedence, binding sources, how claims compose, the marker shape — is on [Trace scoring](/agent-testing/trace-scoring).

This makes the executions list a live quality monitor: filter to low scores over the last hour and read exactly which step failed and why.

## Exploring traces in the Console

The **Observability** page is a filterable table with three views:

- **Task executions** (default) — one row per scored unit: capability, task, conversation, terminal, status, duration, tokens, cost, model, time, and the execution score. **Group by conversation** folds a page's rows under their `conversation.id`.
- **Root traces** — one row per end-to-end run; the only view with bulk selection for datasets.
- **Sessions** — one row per `conversation.id` with rolled-up counts and the session score.

Quick filters cover LLM calls, successes, errors, slow (>5s), expensive (>$0.01), and high-token (≥5k) traces. Filters, sort order, view, and page number all live in the URL, so any slice is a shareable link.

### From traces to datasets

In the **Root traces** view, select rows (or **Select all** across pages) and **Add to dataset**. This is the highest-leverage workflow in Observability: real production behaviour becomes the test set your agent is measured against, one row per trace with its wire transcript, delivered output, score, and a link back to the trace. ## Reading traces over the API

Everything the Console shows is available over REST with the same API key:

```bash
# List root traces (django-filter query params for time, status, capability, service)
curl -H "X-Api-Key: $OVERMIND_API_KEY" \
  "https://api.overmindlab.ai/api/traces/"

# One trace with all of its spans
curl -H "X-Api-Key: $OVERMIND_API_KEY" \
  "https://api.overmindlab.ai/api/traces/{trace_id}/"

# Distinct service names and models, sessions
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/traces/services/"
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/traces/models/"
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/sessions/"

# Task executions (the default view's row grain) and the tasks they bind to
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/task-executions/?capability={id}"
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/behaviours/"
```

Through MCP the same reads are `query_traces`, `query_task_executions`, `query_failures`, and the `overmind://traces/{trace_id}` resource. See the [REST API](/platform/api) page for the full endpoint list.

## Practical guidance

Initialise tracing once, at startup, before the first model call. Give each process its own `service_name` so its telemetry stays separate, and set the capability identity (`capability_id`) from the start. Auto-instrumentation alone produces flat model-call spans and no scoring unit: bracket every agent run with [`overmind.run()`](/tracing/sdk-python#run-the-run-boundary), call `deliver()` on the result, and decorate the functions capability discovery anchors on so each unit binds to its task. Spans that start their own trace outside a run boundary are dropped as orphan fragments. For short-lived processes, flush before exit — `run()` flushes on exit; otherwise call `force_flush_traces()`.
