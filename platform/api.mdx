The console is built on the same REST API you can call directly. Base URL:

```text
https://api.overmindlab.ai
```

An OpenAPI schema and interactive explorer are served by the API itself at `/api/schema/` and `/api/docs/` (Swagger UI).

## Authentication

Three ways to authenticate; the first is right for almost all programmatic use:

| Method | How | Use for |
| --- | --- | --- |
| **API key** | `X-Api-Key: ovr_...` or `Authorization: Bearer ovr_...` | SDKs, OTLP ingest, scripts, CI, the CLI, inference |
| **JWT** | `POST /api/auth/token/` with credentials → short-lived access + refresh tokens (`POST /api/auth/token/refresh/`) | User-context integrations |
| **Console session** | Handled by the console's sign-in | Browser only |

API keys are project-scoped: every request authenticated with a key operates inside that key's project. Keys are created and revoked under **Projects → your project → API keys** or via the API:

```bash
# Create (the key is returned once), list, revoke
curl -X POST -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
  -d '{"name": "ci-key", "expires_in_days": 90}' \
  "https://api.overmindlab.ai/api/auth/api-keys/"
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/auth/api-keys/"
curl -X DELETE -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/auth/api-keys/{id}/"
```

## Endpoint map

Standard REST resources follow Django REST Framework conventions: `GET` list with query-param filtering, `POST` create, `GET/PATCH/DELETE` on `/{id}/`, plus the custom actions listed here.

### Core resources

| Resource | Base path | Custom actions |
| --- | --- | --- |
| Projects | `/api/projects/` | `/{project_id}/memberships/` (list, add, remove) |
| Capabilities | `/api/capabilities/` | `GET .../eval_spec/`, `GET .../prompts/`, `GET .../base-model-throughput/`, `DELETE .../` (soft delete) |
| Agent graph | `/api/agent/` | one call: current capabilities, edges, last scan |
| Traces | `/api/traces/` | list returns root spans with `trace_status` (`live`, `completed`, `interrupted`) and the composed score markers in `feedback_score.trace_scoring`; `GET /{trace_id}/` returns all of a trace's spans; `GET services/`, `GET models/` |
| Sessions | `/api/sessions/` | traces grouped by `conversation.id`, with session scores |
| Task executions | `/api/task-executions/` | one row per scored unit — see [Trace scoring](/agent-testing/trace-scoring#reading-executions-over-the-api) for the filters; `GET /{id}/` adds the observed route, step results and intent; `GET conversation-turns/?conversation_id=` (one row per turn, with scores, task state, and tool calls) |
| Tasks | `/api/behaviours/` | list (execution counts, mean score); `GET coverage/?capability=` (eval-set coverage per task); `GET /{id}/evaluators/`; `GET /{id}/authoring-context/` (the task's contract for task-scoped judge authoring) |
| Datasets | `/api/datasets/` | read, rename and delete; `POST .../remove_datapoints/`, `POST .../activate/`, `GET .../cards/`, `GET .../eval-capabilities/`, `POST .../generate-evals/`, `POST .../context/refresh/`, `GET .../datapoints/`, the `/workshop/` family |
| Dataset builds | `/api/uploads/`, `/api/ingestions/` | the only door that creates a dataset — see [Building a dataset](#building-a-dataset) |
| Jobs | `/api/jobs/`, `/api/job-iterations/` | unified long-running-work records |

## Building a dataset

A dataset is never POSTed into existence. Rows are staged, measured in full, and
only then written — so the counts you approve are the counts that land. The same
sequence backs the console's upload dialog and Brain's dataset tools.

<Steps>
  <Step title="Stage a source">
    A file goes up in chunks (`POST /api/uploads/`, then `PUT /api/uploads/{id}/chunk/?offset=`).
    Traces and existing datasets need no upload.

    `POST /api/ingestions/` opens the build with exactly one source — `upload_id`,
    a trace `selection` or `trace_ids`, or a `source_dataset` to re-read — plus the
    `intent` (`eval` or `ft`) and, for traces, the `surface` (`capability` or `model`).
    Omit `intent` to let the server infer it from the rows.
  </Step>
  <Step title="Read the measurement">
    `GET /api/ingestions/{id}/` reports progress, then exact full-corpus counts:
    accepted, rejected with reasons, the field mapping in force, a before→after
    preview, and `effective` — what a commit would write right now.
    `GET /api/ingestions/{id}/rows/?only=rejected` pages the rows themselves.
  </Step>
  <Step title="Change the question">
    `POST /api/ingestions/{id}/plan/` sets a different intent, surface or column
    mapping, or adds a `split` to produce a Training and an Evaluation dataset from
    one measurement. Any change re-measures; the previous numbers are withheld
    rather than shown against a new plan. `POST .../exclusions/` leaves individual
    rows out.
  </Step>
  <Step title="Commit">
    `POST /api/ingestions/{id}/commit/` writes the measured rows and returns the
    dataset. A commit that cannot reproduce what the scan promised fails instead of
    landing a different dataset. `DELETE /api/ingestions/{id}/` abandons a build.
  </Step>
</Steps>

Intent is fixed at build time and cannot be edited afterwards: converting a dataset
means re-reading it into a new one with `source_dataset`, which records the origin.

## Conventions

- **Filtering** uses django-filter query parameters on list endpoints (the console's filter bar builds exactly these URLs — copy them from your browser).
- **Errors**: `401` unauthenticated, `402` insufficient credits for compute-consuming actions (trace ingest is never credit-gated), `403` plan limits, `404` wrong project or missing resource.
- **IDs** are UUIDs except spans (16-hex `span_id`) and traces (32-hex `trace_id`).
