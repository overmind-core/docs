The console is built on the same REST API you can call directly. Base URL:

```text
https://api.overmindlab.ai
```

An OpenAPI schema and interactive explorer are served by the API itself at `/api/schema/` and `/api/docs/` (Swagger UI).

## Authentication

Three ways to authenticate; the first is right for almost all programmatic use:

| Method | How | Use for |
| --- | --- | --- |
| **API key** | `X-Api-Key: ovr_...` or `Authorization: Bearer ovr_...` | SDKs, OTLP ingest, scripts, CI, the CLI, inference |
| **JWT** | `POST /api/auth/token/` with credentials → short-lived access + refresh tokens (`POST /api/auth/token/refresh/`) | User-context integrations |
| **Console session** | Handled by the console's sign-in | Browser only |

API keys are project-scoped: every request authenticated with a key operates inside that key's project. Keys are created and revoked under **Projects → your project → API keys** or via the API:

```bash
# Create (the key is returned once), list, revoke
curl -X POST -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
  -d '{"name": "ci-key", "expires_in_days": 90}' \
  "https://api.overmindlab.ai/api/auth/api-keys/"
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/auth/api-keys/"
curl -X DELETE -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/auth/api-keys/{id}/"
```

## Endpoint map

Standard REST resources follow Django REST Framework conventions: `GET` list with query-param filtering, `POST` create, `GET/PATCH/DELETE` on `/{id}/`, plus the custom actions listed here.

### Core resources

| Resource | Base path | Custom actions |
| --- | --- | --- |
| Projects | `/api/projects/` | `/{project_id}/memberships/` (list, add, remove) |
| Capabilities | `/api/capabilities/` | `GET .../eval_spec/`, `GET .../prompts/`, `GET .../base-model-throughput/`, `DELETE .../` (soft delete) |
| Agent graph | `/api/agent/` | one call: current capabilities, edges, last scan |
| Traces | `/api/traces/` | list returns root spans; `GET /{trace_id}/` returns all of a trace's spans; `GET services/`, `GET models/` |
| Sessions | `/api/sessions/` | traces grouped by `conversation.id` |
| Datasets | `/api/datasets/` | create (`source` = `upload_id`, `rows`, `text`, `traces`, or `dataset_version_id`), read, rename, delete; `GET .../rows/` (paged, `?source=`, `?version=&cell=`, sort/filter/search), `GET .../rows/{index}/`, `GET .../columns/`, `POST .../query/` (read-only SQL), `PUT .../cells/` (save, `run: true` to execute), `POST .../run/`, `GET .../versions/`, `GET .../versions/{id}/` (cells, deltas, contract, alignment), `.../diff/{other}/`, `.../usage/`, `.../restore/`, `.../delete/`, `POST .../append/`, `POST .../refresh/`, `GET .../export/?fmt=jsonl|csv|training`, `GET .../events/` (SSE), `POST .../generate-evals/`, `POST .../context/refresh/` — see [Building a dataset](#building-a-dataset) |
| Uploads | `/api/uploads/` | chunked file upload that a dataset `source.upload_id` refers to |
| Jobs | `/api/jobs/`, `/api/job-iterations/` | unified long-running-work records |

## Building a dataset

A dataset lands its rows as-is and shapes them in a notebook; a run reads a frozen version. The same sequence backs the console and Brain's dataset tools.

<Steps>
  <Step title="Land a source">
    A file goes up in chunks (`POST /api/uploads/`, then `PUT /api/uploads/{id}/chunk/?offset=`).
    `POST /api/datasets/` with `project`, `name`, an optional `capability`, and exactly one
    `source`: `upload_id` (+ `filename`), `rows` or `text` for pasted data, `traces` (a
    trace-list selection or `trace_ids`, plus `grain`: `task` or `trace`), or
    `dataset_version_id` to copy another dataset's product. The response is the dataset;
    landing runs in the background and `source_spec.landing` clears when the rows are in.
    `POST .../append/` adds rows with the same columns; `POST .../refresh/` re-lands a
    trace selection and picks up only new units.
  </Step>
  <Step title="Shape it">
    `PUT /api/datasets/{id}/cells/` saves the ordered cells (`kind`: `python`, `sql`, `note`;
    `title`; `script`; `output_name`). With `"run": true` it executes them at once; otherwise
    `POST .../run/` runs the draft. A frozen head is never edited: saving cells on one mints
    the next draft. `GET .../events/` streams `cell_started`, `cell_repairing`, `cell_done`, `cell_failed`,
    `run_done` and `run_failed` as server-sent events.
  </Step>
  <Step title="Read the version">
    `GET .../versions/{id}/` returns the cells with their deltas, `contract`
    (`train`, `eval` or `raw`) with the `contract_report` behind it, the `alignment`
    report when a capability is bound, the column manifest and `stats`. `.../diff/{other}/`
    compares two versions; `.../usage/` lists the runs that pinned one.
  </Step>
  <Step title="Pin it">
    Eval runs, optimiser experiments and finetuning jobs take `dataset` and, optionally,
    `dataset_version`; without it the newest frozen version whose contract fits is pinned.
    A draft, a raw product, or a version of another dataset is refused with the reason.
  </Step>
</Steps>

## Conventions

- **Filtering** uses django-filter query parameters on list endpoints (the console's filter bar builds exactly these URLs — copy them from your browser).
- **Errors**: `401` unauthenticated, `402` insufficient credits for compute-consuming actions (trace ingest is never credit-gated), `403` plan limits, `404` wrong project or missing resource.
- **IDs** are UUIDs except spans (16-hex `span_id`) and traces (32-hex `trace_id`).
