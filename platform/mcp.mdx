MCP is the platform's first-class agent surface: an account-aware [Model Context Protocol](https://modelcontextprotocol.io) server at `/api/mcp/` that shares its services with the REST API and the Console. A coding agent connected to it can inspect health and failures, land and shape datasets, author evaluators and run evals, launch and follow training, schedule optimisation runs, and drive connectors and instrumentation — everything except the steps that need your filesystem, which it hands to the [CLI](/platform/cli).

## Setup

Training contract 6.1 adds passive `inspect_training_progress` and intent-first
`cancel_finetune`. A frozen `monitoring` policy is shared across readiness,
preparation, estimates and launch. The inspection tool pages durable checks,
generated examples and frozen sample identities without submitting provider work.
Missing evidence and unsupported provider features stay explicit. Full sample
pages are lossless: oversized responses return an error rather than clipped values.
Development evidence does not replace a final held-out benchmark or authorise
activation. Refresh the connected tool catalogue after a local server update.

Contract 6.2 adds agent-declared `json_fields` generation checks through the same
monitoring policy. Supply bounded JSON Pointers, not inferred field semantics.
Inspection retains per-field correctness/coverage, unscorable references and
technical failures separately; existing jobs keep their pinned worker release.

Contract 6.2.1 keeps `latest_generation_check` visible independently of newer
loss-only checks. Classification `facts.assessment` retains receipt-backed,
sample-scoped majority-baseline and missing-prediction findings. Assessment happens
during collection, never on inspection; worker metrics remain unchanged and no
training action is implied. Inconsistent evidence stays inconclusive.

## Optional plugin

The Codex, Cursor and Claude Code plugins package the existing MCP connection,
Overmind branding and the shared workflow skill. MCP remains the complete
integration: tool descriptions, essential operating guidance, resources and
native prompts are available to clients that do not install a plugin. There is
no separate plugin UI.

The bundled `.mcp.json` targets the hosted API and uses OAuth account sign-in.
The connection can access every active project your account is authorized to access,
including future memberships. Account API keys support the same model; project
API keys retain their narrower access.
For a local or self-hosted deployment, use `overmind init --env local --ide codex`
and `overmind sync`, or configure the intended endpoint directly. Keep one active
MCP connection for the intended account or project; a plugin is optional when that connection exists.

Start with `list_projects`. Its `connection.mcp_url` identifies the endpoint that handled the authenticated request. Compare it with the environment you intended to use. `overmind://interface/current` exposes the same endpoint, permission-scoped tool count and catalog hash. If a client has older tool definitions, refresh `tools/list`; do not infer that missing cached tools are unsupported or silently switch servers. When a visual view is useful, read
`overmind://project/current?project_id=ID` and open its
`console_url`. The server builds this ordinary Console link from `FRONTEND_URL`
and the authenticated project. Resource IDs can identify a more specific
Console page. The browser requires its own Console session, and opening a page
does not authorize mutations.

## Authentication

OAuth connections and account API keys discover authorized projects through `list_projects`. Pass the chosen `project_id` on every project tool and as a query parameter on resource URIs. Membership is checked for each operation. There is no shared selected-project state, so concurrent work cannot switch another request's project. Returned resource links retain the project ID. A project API key can only use its configured project and can omit `project_id`.

Read access exposes read-only tools; mutations require write access. API keys retain expiry, active-user and IP-allowlist checks. OAuth grants request `overmind:read` and/or `overmind:write` and require Console sign-in and explicit consent. Tokens use S256 PKCE, exact redirect matching, one-time codes and resource binding; OAuth tokens are accepted only by MCP. Access tokens expire after one hour. Connections remain authorized until revoked, with no refresh-token time limit. Refresh tokens still rotate; reuse revokes the connection's token family. Disabled accounts and lost project memberships continue to lose access.

Set `MCP_SERVER_URL` to the canonical HTTPS `/api/mcp/` endpoint on a hosted deployment, with `FRONTEND_URL` pointing at its Console. HTTP is accepted only for local loopback development. Configured servers advertise OAuth discovery, public-client registration (`token_endpoint_auth_method: none`), authorization, token and revocation endpoints. API-key connections continue to use `X-Api-Key` or `Authorization: Bearer`.

For OpenAI publishing, set `OPENAI_APPS_CHALLENGE` to the portal's public ownership token; the API serves it at `/.well-known/openai-apps-challenge`. Deploy the backend migration and Console consent route before configuring OAuth in the submission portal, then verify the domain and scan tools.

MCP transport requests use `POST` with `application/json`, from an allowed host and origin, within the protocol's body limit. Authentication failures return `401`; authorization failures return `403`. Tool errors are structured results: `{"error": {code, message, retryable, fields}}`.

The public surface is permission-scoped read/write, not a generic API proxy. Named lifecycle operations include `cancel_dataset`, `retry_deployment` and `retry_data_partition`; inspect their schemas and recovery constraints before use.

Unknown external evaluation request intents are retained as missing, never
replayed, and do not block later inputs. `resume_native_evaluation` accepts the
explicit external stage of a paused collector without a native call ID. Unknown
native submissions still require reconciliation with their saved call ID.

`inspect_operation` with `after` and `limit` to inspect recorded stage changes,

### Jobs

Background work returns a **job receipt** — `kind`, `id`, `status` and an `overmind://jobs/{kind}/{id}` resource — that `get_job` reads back. Kinds: `dataset_run`, `connector_sync`, `eval_run`, `finetune` (alias `finetune_job`), `optimizer` (aliases `optimizer_run`, `optimizer_experiment`) and `deployment`.

Names resolve within the project: capability arguments take an id, key or name; connectors take an id or name; dataset tools prefer the UUID `list_datasets` returned because dataset names are not unique.

## Resources

Read-only project entity state under `overmind://`. Account connections add `?project_id=ID`; follow returned links to preserve scope. Static:

| URI | Content |
| --- | --- |
| `overmind://project/current` | The authenticated project identity, provenance, safe metadata and ordinary `console_url` |
| `overmind://dataset-upload` | CLI guidance for uploading local dataset bytes |
| `overmind://dataset-export` | CLI guidance for downloading a committed dataset |
| `overmind://checkpoint-download` | CLI guidance for downloading an archived checkpoint |
| `overmind://connector-setup` | CLI guidance for `overmind connector add` — provider keys never cross MCP |

Templates: `overmind://capabilities/{capability}`, `overmind://traces/{trace_id}`, `overmind://sessions/{session}`, `overmind://datasets/{dataset}`, `overmind://eval-runs/{eval_run}`, `overmind://eval-sets/{eval_set}`, `overmind://finetunes/{job_id}`, `overmind://deployments/{deployment}`, `overmind://optimizer-runs/{experiment}`, `overmind://connectors/{connector}`, `overmind://jobs/{kind}/{id}`.

Deployment resources accept `?period=1h|24h|7d|30d|all&source=application|all` (defaults: all time and all traffic). For example, `overmind://deployments/{deployment}?period=24h&source=application` returns the selected metrics and activity, including failures and end-to-end response percentiles, from the same services used by the Console.

Each deployment resource also includes a current `worker` section: `state` (`warm`, `warming`, `asleep`, or `unknown`), measurement `available`, runner/input/backlog counts and recent-activity/warming signals. These use the Console's cached measurements and do not wake the model. Worker state is independent of the historical metrics filters, deployment readiness (`status`) and the capability's routing selection (`active_model`). Unavailable counts are null, not zero; recent successful traffic can still establish warmth when provider measurements are unavailable.

## The CLI boundary

Local file transfer is a verified part of the connection, not implied by a working
MCP client. Run `overmind connection check --project-id PROJECT --json` from the
coding environment that will transfer the file. It checks both MCP and the
project-scoped transfer API with the same resolved credentials. A successful
check applies only to that execution environment. A sandbox permission denial
requires the host's scoped approval; Overmind does not disable the sandbox or
switch to a browser or another endpoint.

`overmind connection configure --api-url URL --project-id PROJECT --json` can
configure global Codex MCP and file transfer together using an account key already
available locally. It does not pin a project globally or grant network access.
Reload the MCP client after configuration.

Uploads now retain a durable project-scoped receipt binding file SHA-256, byte
count and destination settings. Repeat the same command after interruption; it
resumes stored bytes or recovers the already-published dataset. Use an explicit
`--request-key` to manage the identity yourself; changed inputs under that key
conflict. `get_job(kind=dataset_transfer)` reports measured bytes and publication
without starting work. `dataset_run` reports subsequent extraction/landing.
Transfer protocol version 1 is advertised by `overmind://interface/current`.

For a JSON wrapper, `overmind dataset upload FILE --json-rows-field pairs
--project-id PROJECT --json` explicitly selects the top-level `pairs` array.
The original file, wrapper metadata and selection provenance remain retained.
This selection says nothing about label meaning or training readiness.

Three things never cross MCP: file bytes, repository edits, and provider secrets. A dataset file goes up with `overmind dataset upload`; a dataset or checkpoint comes down with `overmind dataset export` and `overmind model download-checkpoint`; repository discovery is `/overmind setup` then `overmind sync`; an optimisation run's candidates are generated and replayed by `overmind optimise` in your checkout; a model swap is a prompt (`get_model_swap_prompt`) the agent applies with its own editing tools; a connector's provider key is entered with `overmind connector add` in a terminal. The prompts above name the exact command at each handoff, and `--json` on the CLI returns the ids the agent needs to continue.

## Training supervision

`start_finetune` accepts `supervision_policy`; its context is derived from the selected capability, repository, behaviour contracts and frozen datasets without requiring an objective prompt.

Use `get_training_supervision(job, offset, limit)` to inspect checkpoint pages, evidence and acknowledged interventions. `investigate_training` queues a durable assessment; its optional message does not redefine the benchmark.

`control_training` requests a checkpoint, bounded learning-rate reduction, pause or resumable stop. Reuse its idempotency key when retrying. Requested and delivered commands are not applied until the trainer acknowledges them. `resume_training` continues a confirmed paused or stopped attempt from a verified checkpoint.

`set_training_supervision_policy` changes mode and allowances with an expected policy revision. `select_training_checkpoint` selects a ready deployment for review and `run_inference`; activation remains the separate `set_active_model` operation.

All operations use project-scoped authorization and the same services as the Console. The `overmind://finetunes/{job_id}` resource exposes the same supervision state. Supported controls and intermediate serving availability are explicit in each run's capabilities.

### Progress and feedback latency

Supervision distinguishes warm-up, early learning, learning, delayed feedback,
confirmation, awaiting an intervention outcome, and finishing. The same `feedback`
object is available in Console, REST and MCP, including evaluated/current steps,
action eligibility and reasons, outstanding checkpoint work, and open data reviews.
Early checkpoints establish measurements; a low early score alone never justifies
an adjustment. Defaults require 10% of training and warm-up to finish, allow at
most 15% of the run's steps as feedback lag, and reserve at least the configured
cooldown or 5% of training before measuring an intervention's outcome. These are
configurable controller limits, not universal claims about model convergence.

Intermediate evaluations use a reproducible stratified monitoring panel (40 rows
by default), with full evaluations for the initial reference, confirmation of a
sustained regression, and post-adjustment outcomes. Panel and full scores are
labelled separately. Final evaluations still use the entire pinned evaluation
cell. The evaluation allowance counts both panel and full evaluations; an
adjustment is withheld if no allowance remains to measure its outcome.

Only one checkpoint evaluation is in flight per attempt; obsolete waiting versions
are skipped for automatic evaluation without deleting their weights. Live
checkpoint generation and judging take priority over ordinary evaluation work in
the same workers, with one prefetched task per worker slot. Completed results from
another attempt or incompatible judging context cannot justify a correction.
A proposal is checked again before dispatch, and protocol-2 trainers reject it if
its evidence step window has passed. Older running trainers retain manual controls
and observation but cannot apply these bounded automatic commands until resumed
on the updated worker. After an adjustment, a new observation window and comparable
post-change evidence are required. Unresolved data reviews stay visible without
being requested again at every training interval.

If feedback cannot arrive soon enough, the platform reports delayed feedback and
withholds automatic adjustments. It does not silently extend training, increase
budgets, change datasets or activate a model. Numerical instability still stops
locally. Recovery after an intervention is a measured association, not proof of
causality; monitoring remains development feedback rather than an untouched test.

## Data-first model workflows

Invoke `develop-model-from-data` for the supported path from uploaded data to reproducible model comparisons. The Workshop performs initial exploration and saves target interpretation. Repository scanning and capabilities are optional.

- `create_data_partition` and `retry_data_partition` save or resume group-preserving role assignments.
- `list_decision_models` discovers eligible foundation, trained and external decision participants.
- `create_native_evaluation` and `resume_native_evaluation` execute frozen standalone comparisons with optional calibration.
- `create_training_experiment` saves explicit candidates; `launch_training_experiment` launches the saved set within the user's authorization.
- `measure_decision_performance` and `resume_decision_performance` measure a saved client workload after quality scoring.
- `list_model_workflows`, `get_job` and returned job resources expose protocols, receipts, reports and uncertainty.

Reuse request keys and saved call IDs. Keep references out of provider inputs, preserve unresolved submissions, and distinguish recorded costs from estimates and missing invoice components. These workflows share domain services with Console/REST and do not activate a production model. Local file bytes still use the supported CLI upload/export path.

Native evaluations automatically recover transient stage interruptions with bounded backoff. While `get_job` reports running, poll it; stage calls retain `retry_at`, consecutive failure counts and recovery history. Completed predictions and saved native calls are reused. Only missing external predictions with a recorded transport failure are retried, with uncertain costs retained. Exhausted or permanent collection errors finish scoring available verified predictions. The job is `completed`, with `results.completion.status=completed_with_issues`, per-suite/per-participant coverage and issue details. Missing outputs are not zero scores; paired comparisons use shared scored inputs and partial coverage can bias results. Incomplete calibration leaves raw scores available. Verification/report failures and unresolved submission intents still require inspection; paused runs require explicit resume.


## Durable data-first workflows

The `author-dataset-transformation` prompt guides native agents through inspecting,
authoring, testing, retaining and adapting conditional transformations. In contract
5.2, `inspect_dataset_workbench(pipeline=REVISION_UUID)` retrieves an exact revision,
its paged family history and its runs/bindings. Package resources page complete
retained code with `file`, `offset`, `limit` and `next_offset`. Family updates use
`expected_revision`; stale changes return `revision_conflict`. Conditions describe
agent-authored routing, not independently verified branch coverage. Verify row
members and intended partition coverage, not only successful tool calls.

Read `overmind://interface/current` for the connected contract version and catalog fingerprint. Account connections select an authorized project on each call. Data-only projects require neither a repository scan nor a capability.

`inspect_dataset_workbench` exposes immutable pipeline recipes and execution receipts. `get_job(kind=dataset_pipeline)` reads one exact run. `cancel_dataset` prevents publication without claiming remote termination. Stable request keys recover existing work; changed payloads conflict. There is no platform-agent workflow control endpoint.

`explore_dataset` profiles an explicit source cell in background and reports sampling feasibility and paginated allocations. `derive_dataset` preserves a frozen historical source in a new chain with lineage. Workshop target interpretation records evidence references, scope, hypotheses and conflicts; technical validation never invents label meaning.

`create_native_evaluation` saves a draft. `prepare_native_evaluation` verifies its frozen suites without submitting inference. `launch_native_evaluation` starts the authorized saved comparison once. Independent participants progress concurrently while calibration and final dependencies remain enforced. `pause_native_evaluation` stops new work; submitted provider calls may still finish. Resume from saved receipts, and never repeat a submission with unknown acknowledgement.

Completed native evaluation jobs return compact summaries with coverage counted across every benchmark. Use `report.json_path` or `report.markdown_path` on the same server with the existing API credential to download the complete results. The JSON report includes all raw and calibrated per-benchmark metrics, paired confidence intervals, failures and diagnostic slices. Calibration scores are in-sample. Summary macros are not individual benchmark scores.

`create_training_experiment` saves purpose, candidates and an optional comparison protocol. `prepare_training_experiment` produces a forecast bound to that configuration. `launch_training_experiment` uses the saved authorization and optional user-defined planning constraints; no monetary cap is imposed by default. A planning allowance is not a provider-enforced invoice limit. `create_training_profile` creates an explicit bounded measurement candidate before larger training.

Use `reuse_evaluation_predictions`, or an experiment's explicit `reuse_existing_predictions` choice, to reuse matching completed predictions with recorded lineage. Input, model, runtime and inference conditions must match. Independent repetitions and performance measurements are never silently cached. `measure_decision_performance` may run once model/runtime identity is qualified, before final quality scoring finishes.

Compact receipts contain next operations, required arguments, whether input is needed, polling guidance and links to full evidence. A reconnecting client can use `list_model_workflows` and `get_job` to recover the objective and progress without prior chat history. Report verified artifacts, coverage and failed arms as well as successful child jobs.
