MCP is the platform's first-class agent surface: an account-aware [Model Context Protocol](https://modelcontextprotocol.io) server at `/api/mcp/` that shares its services with the REST API and the Console. A coding agent connected to it can inspect health and failures, land and shape datasets, author evaluators and run evals, launch and follow training, schedule optimisation runs, and drive connectors and instrumentation — everything except the steps that need your filesystem, which it hands to the [CLI](/platform/cli).

## Setup

`overmind init --ide <client>` writes the entry and `overmind sync` fills in the project key, which is what the [Quickstart](/quickstart) prompt does for you. The entry is a streamable-HTTP server with an `X-Api-Key` header:

<CodeGroup>

```json Cursor (.cursor/mcp.json)
{
  "mcpServers": {
    "overmind": {
      "url": "https://api.overmindlab.ai/api/mcp/",
      "headers": { "X-Api-Key": "ovr_…" }
    }
  }
}
```

```json OpenCode (opencode.json)
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "overmind": {
      "type": "remote",
      "url": "https://api.overmindlab.ai/api/mcp/",
      "enabled": true,
      "headers": { "X-Api-Key": "ovr_…" }
    }
  }
}
```

```bash Claude Code
claude mcp add --scope local --transport http overmind https://api.overmindlab.ai/api/mcp/ --header "X-Api-Key: ovr_…"
```

</CodeGroup>

Codex takes the same entry in `.codex/config.toml`. Claude Code keeps the key in local scope (`~/.claude.json`), outside the repository. Self-hosted: replace the URL with your API host plus `/api/mcp/`, for example `http://localhost:8000/api/mcp/` (`overmind init --env local`, or `--api-url`).

Behind TLS termination, MCP derives its public request scheme using Django's `SECURE_PROXY_SSL_HEADER` setting, just like REST. The trusted proxy must set `X-Forwarded-Proto` from the original connection and prevent clients from spoofing it. `list_projects` and `overmind://interface/current` must report the same HTTPS MCP address used by `overmind connection check`; an HTTP address here is a server configuration or deployment fault, not a reason to downgrade the client or disable endpoint validation.

## Optional plugin

The Cursor, Claude Code and Codex plugins bundle the MCP connection, Overmind branding and the [workflow skills](#workflow-skills). MCP alone is the complete integration: tool descriptions, operating guidance, resources and prompts reach every client, with or without a plugin.

Install it from the `overmind-core/overmind` repository:

| Client | Install |
| --- | --- |
| Claude Code | `/plugin marketplace add overmind-core/overmind`, then `/plugin install overmind@overmind` |
| Codex | `codex plugin marketplace add overmind-core/overmind`, then enable Overmind in `/plugins` |
| Cursor | Add `overmind-core/overmind` as a plugin marketplace, then install Overmind |

The plugin's MCP entry points at the hosted API and signs in with OAuth. The connection reaches every active project your account can access, including projects you join later. For a self-hosted deployment, run `overmind init --env local --ide <client>` and `overmind sync` instead. Keep one active Overmind MCP connection per client.

Start with `list_projects`. To see a project in the browser, read `overmind://project/current?project_id=ID` and open its `console_url`, which the server builds from `FRONTEND_URL`. The browser needs its own Console sign-in, and opening a page grants no write access.

## Authentication

**Account connections.** OAuth connections and account API keys find the projects you can access with `list_projects`. Pass the chosen `project_id` to every project tool, and as a query parameter on resource URIs. Membership is checked on every operation, and there is no shared "current project", so parallel work cannot switch another request's project. Returned resource links keep the project id.

**Project API keys** reach only their own project and can omit `project_id`.

**Permissions.** Read access exposes the read-only tools; writes need write access. API keys keep their expiry, active-user and IP-allowlist checks, and authenticate as `X-Api-Key` or `Authorization: Bearer`.

**OAuth.** A grant asks for `overmind:read` and/or `overmind:write`, and needs Console sign-in and explicit consent. Tokens use S256 PKCE, exact redirect matching, one-time codes and resource binding, and only MCP accepts them. Access tokens expire after one hour. A connection stays authorized until it is revoked: refresh tokens have no time limit, but they rotate, and reusing an old one revokes the connection. A disabled account or a lost project membership ends access.

**Hosting.** On a public deployment, set `MCP_SERVER_URL` to the HTTPS `/api/mcp/` endpoint and `FRONTEND_URL` to the Console. Plain HTTP is accepted only on local loopback. The server then advertises OAuth discovery, public-client registration (`token_endpoint_auth_method: none`), and the authorization, token and revocation endpoints. To publish the server as an OpenAI app, set `OPENAI_APPS_CHALLENGE` to the portal's ownership token; the API serves it at `/.well-known/openai-apps-challenge`.

**Transport.** Requests are `POST` with `application/json`, from an allowed host and origin, within the protocol's body limit. Authentication failures return `401` and authorization failures `403`. Tool errors are structured results: `{"error": {code, message, retryable, fields}}`.

The public surface is read and write only. There are no delete or generic API tools. The lifecycle exceptions are `retry_deployment`, for exactly the failed-or-deleted deployment case, and `cancel_dataset_job`, which stops a dataset import or script run and keeps nothing it produced.

## Tools

Forty-six tools, each with a strict input and output schema the client reads at call time. Every result carries the same object twice — as `structuredContent` and as compact JSON text — plus resource links for the entities it touched. Arguments marked `?` are optional.

Project tools also accept `project_id`, required for account connections. `list_projects` and `get_model_catalog` do not need a project.

**Versions.** Every dataset version argument is `version` (a label such as `v3`, or the version id), with `eval_version` and `validation_version` for the other datasets of a job; `parent`, `from`, `to` and `expected_active` take the same values. Omitted, a tool reads the dataset's active version. Launch tools pin the versions they used and return them.

**Retries.** `create_dataset`, `start_finetune`, `start_decision_job` and `run_evaluation` accept `request_key`. The same key within 24 hours returns the first result instead of starting the work again.

| --- | --- | --- |

| `create_dataset` | `name`, `source`, `intent?`, `capability?`, `split?`, `request_key?` | Land a new dataset from one `source`: `{kind: "traces", trace_ids?, filters?, search?, limit?}` (one row per trace), `{kind: "llm_calls", since, until?, model?, limit?}` (one row per `llm_call` span, `limit` 200 by default and at most 10,000; needs `capability`, and `intent` or `split`) or `{kind: "version", dataset, version?}` (a version of a project dataset, keeping its intent and capability unless given). | `try_dataset_script` | `dataset`, `parent?`, `script`, `attachment?` | Run a script on a version in the sandbox and preview the result: rows, columns, three rows, printed output. Creates nothing |
| `probe_dataset_version` | `dataset`, `version?`, `script` | Run a script on a version and return what it prints |
| `add_dataset_version` | `dataset`, `parent?`, `title`, `script`, `attachment?` | Run a script on a parent version and store the result as a new, inactive version with its impact |
| `add_synthetic_examples` | `dataset`, `parent?`, `rows`, `instruction` | Append 1–50 rows you wrote as a new, inactive version, with the instruction as their lineage |
| `diff_dataset_versions` | `dataset`, `from?`, `to?` | Compare two versions row by row on `source_row` |
| `activate_dataset_version` | `dataset`, `version`, `expected_active?` | Make a version the one training, evaluation and the optimiser read by default; `expected_active` refuses with `active_conflict` when the active version moved |
| `update_dataset` | `dataset`, `name?`, `intent?`, `capability?` | Set the name, intent or capability |
| `resume_dataset_import` | `dataset` | Retry a blocked source import |
| `cancel_dataset_job` | `dataset`, `run?` | Stop the dataset's import (both datasets of a split), or with `run` one queued or running script run. Nothing it produced is kept; a finished import or run returns its state |

Source-import admission is visible in `get_job(kind="dataset_run").progress.admission`
and dataset-operation `landing_admission`. These report waiting, admitted, running
and terminal states with measured timestamps. A queued request consumes no
execution attempt; a lost started import retains its source and requires
`resume_dataset_import`. Repeat the existing receipt's poll rather than creating
another import.

`attachment` is the `upload_id` from `overmind dataset attach FILE --json`; the script reads the table as the frame `attachment`. See [Rows made outside Overmind](/core/datasets#rows-made-outside-overmind).

Script runs are idempotent. A call that returns `queued` or `running` is still working: poll the `dataset_run` job it returns with `get_job`, or repeat the identical call. The same parent and script, and the same attached file, return the same version. A failed run creates no version, and the identical call returns that failure for an hour unless the platform caused it (`transient: true`). A stopped run is not reused: the identical call runs it again. A run that waits 15 minutes for a project slot fails with `transient: true`. See [Datasets](/core/datasets#shape-it-from-your-agent).

`start_finetune` and `check_finetune_readiness` use the train dataset's capability unless you pass `capability` (`null` for none). Pass `eval_dataset` and `eval_set` unless that capability owns exactly one eval dataset whose active version fits, and has an active eval set; another capability's eval data is never chosen. For a split, pass its eval half as `eval_dataset`.

`run_inference` uses the production serving output reservation when `max_tokens` is omitted or null (currently 8,192 tokens). Explicit positive integer budgets have no MCP-specific ceiling. The model server validates the templated input plus reserved output against the deployment's context; an oversized request returns `context_length_exceeded` without silently reducing its budget. Generation exhaustion is reported by `finish_reason` and `truncated`. The MCP response's `content` is separately bounded to 32,000 characters, with `content_clipped` indicating any response clipping.

### Jobs

Background work returns a **job receipt** — `kind`, `id`, `status` and an `overmind://jobs/{kind}/{id}` resource — that `get_job` reads back. Kinds: `dataset_import`, `dataset_run`, `connector_sync`, `eval_run`, `training_preparation`, `finetune` (alias `finetune_job`), `optimizer` (aliases `optimizer_run`, `optimizer_experiment`), `deployment`, `model_activation` and `decision_job`.

Names resolve within the project: capability arguments take an id, key or name; connectors take an id or name; dataset arguments take a name only when it is unique, so pass the UUID `list_datasets` returned.

## Resources

Read-only project entity state under `overmind://`. Account connections add `?project_id=ID`; follow returned links to preserve scope. Static:

| URI | Content |
| --- | --- |
| `overmind://project/current` | The authenticated project identity, provenance, safe metadata and ordinary `console_url` |
| `overmind://dataset-upload` | CLI guidance for uploading local dataset bytes |
| `overmind://dataset-export` | CLI guidance for downloading a committed dataset |
| `overmind://decision-models` | Trainable decision models and the decision row format |
| `overmind://checkpoint-download` | CLI guidance for downloading an archived checkpoint |
| `overmind://connector-setup` | CLI guidance for `overmind connector add` — provider keys never cross MCP |

Templates: `overmind://capabilities/{capability}`, `overmind://traces/{trace_id}`, `overmind://sessions/{session}`, `overmind://datasets/{dataset}`, `overmind://eval-runs/{eval_run}`, `overmind://eval-sets/{eval_set}`, `overmind://finetunes/{job_id}`, `overmind://deployments/{deployment}`, `overmind://optimizer-runs/{experiment}`, `overmind://connectors/{connector}`, `overmind://jobs/{kind}/{id}`.

Deployment resources accept `?period=1h|24h|7d|30d|all&source=application|all` (defaults: all time and all traffic). For example, `overmind://deployments/{deployment}?period=24h&source=application` returns the selected metrics and activity, including failures and end-to-end response percentiles, from the same services used by the Console.

Each deployment resource also includes a current `worker` section: `state` (`warm`, `warming`, `asleep`, or `unknown`), measurement `available` and recent-activity/warming signals. These use the Console's cached measurements and do not wake the model. Worker state is independent of the historical metrics filters, deployment readiness (`status`) and the capability's routing selection (`active_model`). Recent successful traffic establishes warmth when measurements are unavailable.

## The CLI boundary

Three things never cross MCP: file bytes, repository edits, and provider secrets. A dataset file goes up with `overmind dataset upload`, and a table for a script with `overmind dataset attach`; a dataset or checkpoint comes down with `overmind dataset export` and `overmind model download-checkpoint`; repository discovery is `/overmind setup` then `overmind sync`; an optimisation run's candidates are generated and replayed by `overmind optimise` in your checkout; a model swap is a prompt (`get_model_swap_prompt`) the agent applies with its own editing tools; a connector's provider key is entered with `overmind connector add` in a terminal. The prompts above name the exact command at each handoff, and `--json` on the CLI returns the ids the agent needs to continue.

## Workflow skills

`overmind init` installs the workflow skills next to the MCP entry, and the optional plugin bundles the same files. The main `overmind` skill covers setup, repository discovery and work that spans several surfaces. Each focused skill covers one surface:

| Skill | Workflow |
| --- | --- |
| `overmind-agent` | Capability map, behaviour coverage and repository provenance |
| `overmind-observability` | Trace investigations, failures, latency and instrumentation gaps |
| `overmind-datasets` | Landing, shaping datasets with scripts, versions, synthetic examples and export |
| `overmind-evaluations` | Evaluators, eval sets, runs and baseline comparisons |
| `overmind-optimiser` | Prompt and code experiments, and model comparisons |
| `overmind-training` | Exact data preparation, costs, fine-tuning, decision models and held-out evaluation |
| `overmind-inference` | Serving metrics, worker state, live routing, activation and decision requests |
| `overmind-integrations` | Tracing providers, boundary mappings and verified imports |

`overmind skills list --verbose` prints the installed catalog. `overmind skills sync <names> --ide <client>` refreshes the named skills, and `overmind init --ide <client>` installs the full set.

`/overmind onboard`, `setup`, `ensure-tracing`, `dataset`, `finetune`, `optimise` and `backtest` load the main skill's references: Cursor through command files, Claude Code through the skill itself. In OpenCode and Codex, ask for the step by name. The main skill is the only place the local scan (`/overmind setup`) lives; the native prompts cover the server-side workflows.

MCP SQL inspection defaults to eight concurrent queries across API workers and two
per project. `overmind://interface/current` reports the deployed budgets. On
`query_capacity_busy` or `query_capacity_unavailable`, wait at least the returned
`retry_after_seconds` and retry identical SQL against the returned exact cell.
Do not fan out retries; use retained dataset pipelines for bulk analysis.
