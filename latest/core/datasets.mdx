A dataset is the curated slice of your data that eval runs, optimisation runs, and training runs consume. Overmind treats it as one chain:

| Thing | What it is | Who writes it |
| --- | --- | --- |
| **Source** | The rows exactly as they arrived — a file, pasted rows, or a trace selection. Version 1.0 | Landing. Never edited |
| **Cell** | One Python transformation over the previous frame. Each cell that ran is the next version: 1.1, 1.2, … | You, or the dataset's agent |
| **Active version** | The cell a run reads: the last one that ran unless you set another | You |

Two things describe what the table is for: the **intent** (`train` or `eval`) and the **capability** it belongs to. Landing proposes both from the rows, you can change either on the page, and both freeze the moment a version is used. Every version carries two measured contracts against them.

Nothing is reshaped on the way in and nothing is edited in place. To change the table you change a cell and run again; the cells after it run again in place and keep their version numbers. A version a run has read is frozen: its script is read-only, its frame cannot change, and so is every cell before it.

## Landing a source

<Tabs>
  <Tab title="From traces">
    Select rows in [Observability](/latest/core/observability#from-traces-to-datasets) and **Add to dataset**, or land every trace matching the current filters. Choose what one row is: a **task** (the unit [trace scoring](/latest/agent-testing/trace-scoring) judges, with the reconstructed `messages`, `tools`, `input`, `output`, the bound `behaviour_key`, every judge's `verdicts`, `success_score`, cost and token counts, and the `trace_id`/`unit_span_id` lineage), a whole **trace**, or one **assistant turn** (the transcript up to that turn). The dialog shows the row count each grain gives before you land.
  </Tab>
  <Tab title="Upload or paste">
    Drop a **CSV, TSV, JSON, JSONL, or Parquet** file anywhere on the Datasets page, or paste rows straight into the dialog. Columns and types are read from the file; numbers stay numbers, nested JSON stays JSON.
  </Tab>
</Tabs>

Landing writes the source as Parquet, stamps every row with a `source_row` index so later versions can be diffed value by value, scores every capability of the project against the rows (bound ids, the system turn, tool names, input keys) to propose one, and proposes the intent from the shape: transcripts with assistant turns are train, an input with a reference is eval, anything else is **pending** until the agent decides.

<Warning>
A cell value larger than about 200 KB (a tool call carrying a serialised agent state, say) is cut to a preview marker on the way in. The row and every other column land intact.
</Warning>

## The workshop

Opening a dataset lands you in the Data Workshop: a version strip down the left edge, the cells stacked in the middle, and the dataset's agent on the right. There is no header: the name, the intent and the capability are the agent's to change, from the chat.

- A cell is a title, a Python body and the frame it left. The body reads the previous frame as `df` (pandas, with `pd` and `np` bound) and leaves the next one in `df`. It runs in an isolated interpreter with a CPU and memory cap, no file or network access, and imports from the workshop's library list: the standard library, pandas, numpy, pyarrow, DuckDB, scipy, scikit-learn, rapidfuzz, tiktoken and a few more, plus a short list the agent can install on request.
- Under the script, the table marks new rows and changed values against the cell before, with the old value on hover.
- The active version's cell carries the consumers: a train table offers **Train a model**; an eval table offers **Run the optimiser** and **Use in a training job** (the eval dataset that scores the job). Export sits in the cell's title chip. Any other version offers **Set active**.

**Run** executes every cell whose script or input changed. A failing cell shows its traceback, the cells after it stay queued, and the last good version stays active; fix the cell and run again.

### The agent

The chat on the right is the dataset's own agent, a Cursor session with ten tools over the chain and a workspace that holds the capability card, the library list, one file per cell, and every version's frame. It writes a script, tests it against a version, and only then lands a cell, so a cell that lands has already run once.

The first landing starts one turn. It decides a pending intent, lands the fewest cells that make the active version meet both contracts, each run as it lands, then runs the quality checks an engineer would run for that intent — refusals and truncated turns, duplicates, length outliers, tool calls that do not parse, leakage of the reference into the input, behaviour coverage — and lands one cell per finding that has rows behind it, run at once, with the count in its note. A fix that would drop more than half the rows lands as a **proposal** instead: it waits in the chat as a card with **Run** and **Discard**, never in the notebook — Run lands and runs it, Discard drops it. The name, the intent and the capability change through the chat too (ask the agent; a used version fixes the intent and the capability), and changing either re-measures every version. When a contract fails, the contract chip on the active version suggests only the moves that would change the verdict: **Ask Overmind to fix it** sends one turn on that contract alone (no quality pass); the other intent is offered when its shape already holds; a better-ranked capability is offered when the capability contract is the one failing. Each suggestion is a chat turn: the agent makes the change and re-aligns the chain.

After that the conversation is open. A request that changes the data is one new cell, run at once. A request to change an existing cell edits it in place and re-runs from there. A question is answered from the status, a query, or a diff between two versions.

## Contracts

Every version is measured against two contracts, and the page reports whether the active version fits the intent:

| Intent | Shape | Capability, row by row | Feeds |
| --- | --- | --- | --- |
| **Train** | A `messages` column whose every row is a chat transcript with an assistant turn (`tools` optional) | The system turn is the capability's synced system prompt; every tool call names a declared tool | [Training](/latest/models/training) |
| **Eval** | An `input` on every row and an `expected_output` column with at least one reference | Every `input` carries the capability's required input keys | [Eval runs](/latest/agent-testing/eval), the [Optimiser](/latest/agent-testing/optimisers), backtests |

The capability contract is vacuous when the capability declares nothing. Rows that fail are counted with the reason; a row that cannot meet a contract is a finding for the agent, never a default value. A training job whose eval dataset shares `trace_id`s with the train version is refused until they are separated.

## Versions and uses

Every run — eval, optimiser, training — **uses** the version it read and links back to it. A use freezes that version and every cell before it, starts a new major number (1.3 becomes 2.0, the cells after it become 2.1, 2.2, …), and protects the frame: it cannot be deleted, and neither can its dataset. The worker re-hashes the frame before it starts, so a run never silently reads a file that changed underneath it.

## API

```bash
# List, read, rename, delete
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/datasets/?project=<project-uuid>&intent=eval"
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/datasets/{id}/"

# Create from pasted rows (a file goes through /api/uploads/ first; traces take a selection)
curl -X POST -H "X-Api-Key: $OVERMIND_API_KEY" -H "Content-Type: application/json" \
  -d '{"project": "<project-uuid>", "name": "triage-eval", "intent": "eval",
       "source": {"rows": [{"input": "...", "expected_output": "..."}]}}' \
  "https://api.overmindlab.ai/api/datasets/"

# Rows of a version with diff marks, column stats, read-only SQL over table t
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/datasets/{id}/rows/?cell=<cell-id>&diff=1&limit=50"
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/datasets/{id}/columns/"
curl -X POST -H "X-Api-Key: $OVERMIND_API_KEY" -H "Content-Type: application/json" \
  -d '{"sql": "SELECT count(*) FROM t"}' "https://api.overmindlab.ai/api/datasets/{id}/query/"

# Add a cell, run the chain, talk to the agent; /events/ streams cells, runs and chat
curl -X POST -H "X-Api-Key: $OVERMIND_API_KEY" -H "Content-Type: application/json" \
  -d '{"title": "Keep", "script": "df = df[df[\"tag\"] == \"keep\"]"}' "https://api.overmindlab.ai/api/datasets/{id}/cells/"
curl -X POST -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/datasets/{id}/run/"
curl -X POST -H "X-Api-Key: $OVERMIND_API_KEY" -H "Content-Type: application/json" \
  -d '{"message": "Drop rows whose answer is under ten tokens"}' "https://api.overmindlab.ai/api/datasets/{id}/chat/"

# Who used a version; export a version (a use — the response names it in
# X-Overmind-Cell / X-Overmind-Version / X-Overmind-Fingerprint)
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/datasets/{id}/cells/{cell}/usage/"
curl -H "X-Api-Key: $OVERMIND_API_KEY" "https://api.overmindlab.ai/api/datasets/{id}/export/?fmt=jsonl&cell={cell}"
```

The full surface is in the [API reference](/latest/platform/api#building-a-dataset).

## Getting the most out of it

Start small and real: 10–50 representative trace-sourced rows beat a thousand synthetic ones for almost every purpose. Let the first pass tell you the shape, read the proposals for the rest. When the same defect keeps appearing in fresh trace batches, that is usually a signal about the agent, not the data.
