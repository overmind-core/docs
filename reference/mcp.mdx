The Streamable HTTP endpoint is `/api/mcp/` on the selected deployment. MCP shares domain services with REST and the Console. It is not a generic HTTP proxy.

Use this after [connecting Overmind](/how-to/connect). Supply or select the named resource in your conversation; the agent reads the contract rather than guessing IDs.

## Discovery and scope

| Surface | Contract |
| --- | --- |
| `list_projects` | Authorized active projects, pagination and `connection.mcp_url` |
| `overmind://interface/current` | Connected contract version, permission-scoped catalogue fingerprint and interface metadata |
| Project tools | Account connections pass `project_id` explicitly |
| Project resources | Add `?project_id=PROJECT_ID` or follow the returned scoped link |
| Project API key | Restricted to its bound project |

Use the connected `tools/list`, `prompts/list` and resources for complete argument schemas. Tool availability depends on permissions and the deployed version; a static tool count is not a capability guarantee.

## Authentication

Account connections sign in with OAuth through the deployment's login and consent flow; `overmind init` configures this. API-key connections use `X-Api-Key` or a supported bearer header. Account keys reach authorized projects; project keys retain narrower scope. MCP OAuth tokens do not authenticate ordinary CLI file transfers.

Read permission exposes inspection operations; writes require the operation's permission scope. Expiry, account state and membership continue to apply.

| --- | --- |

| `overmind://dataset-export` | Version export guidance |
| `overmind://checkpoint-download` | Checkpoint download guidance |
| `overmind://connector-setup` | Provider-credential CLI handoff |

Follow returned resource links for packages, revisions, bindings and data-first workflows. Their identifiers and pagination belong to the connected contract.

## Jobs, pagination and retries

Background operations return durable identities. `get_job(kind=..., id=...)` reads the receipt; `inspect_operation` pages stored events without waking a worker. Use returned polling guidance while active and next actions after completion.

Requests that accept a stable key recover the same work when the key and payload match. Changed payloads conflict. Do not assume every mutation is idempotent: `run_evaluation`, for example, creates new runs.

Pagination can be limited by both item count and response bytes. Follow returned cursors, offsets, `collections` descriptors and `evidence_resource` links for complete retained evidence.

Tool errors include a structured code, message, retryability and field details where applicable. Authentication and authorization failures remain distinct from workflow failures.

## Prompts and local handoffs

Prompts include `author-dataset-transformation`, `develop-model-from-data`, `investigate-capability`, `instrument-repository`, `prepare-evaluation`, `evaluate-change`, `finetune-capability`, `optimize-capability`, `compare-models`, `ship-model`, `upload-dataset-file`, `export-dataset`, `connect-traces` and `download-checkpoint`.

The CLI transfers bytes and runs local repository work. Provider secrets enter protected local configuration or the appropriate Console flow, not MCP tool arguments. See [Connect your coding agent](/how-to/connect).


## Agent activity and setup progress

The Console bell shows saved outcomes from coding-agent actions alongside running jobs.
Entries are short sentences with the reported coding client when known and inline
navigation chips for recorded tasks and affected assets. Unknown or ambiguous clients use a generic label;
a connection milestone does not establish that an agent is currently working.

After connection, the main landing page replaces the getting-started prompt with the
current SDK’s ten onboarding stages: install, connect, inspect, discover, describe,
verify references, write snapshot, validate, sync, and instrument capabilities. Data onboarding keeps its upload flow without a setup checklist.
The notification bell has one activity feed. The coding agent reports verified completed
stages with `report_onboarding_progress(project_id, run_id, completed_steps)` (0–10),
reusing one UUID `run_id` per attempt. Local-stage completion is agent-reported; it
is not independent server verification. Progress reports do not create notifications.
Retries retain progress, and a new run ID starts a separate attempt. Historical local
work without a progress receipt stays unreported.

Read the same records through `overmind://activity?project_id=PROJECT_ID`. Use `offset`
and `limit` (1–100) to page activity, and `path=agent` or `path=data` to inspect setup
milestones. Repository sync, source upload and landing, preparation publication and the
first received trace advance milestones only when their evidence is recorded. Historical
work without an activity receipt stays unrecorded.

Status checks, inspections and polling do not create action notifications. Initialization
records a one-time connection milestone. Job state changes update the saved task activity;
retries reuse the same receipt. The Console keeps read state per user, and reading the
MCP resource never acknowledges notifications.

The Console receives project-scoped activity snapshots through a live connection.
Task rows evolve in place, and affected asset views refresh their data without a page
reload. Newly observed changes briefly highlight the affected row or card; historical
activity does not flash on page load. Reconnecting reconciles the saved state.

The dataset inventory shows attached uploads with measured byte progress and distinguishes
queued work, transformations, previews, imports, and failed datasets. Published versions
and row counts remain visible while new work is underway. MCP job receipts remain the
source for detailed progress; viewing or refreshing the table creates no action records.

Onboarding milestones include the recorded coding agent name and kind. The Console shows that reporter beside the current stage. Repository setup must report verified progress through MCP at every stage transition, including when resuming with older installed skills; chat updates alone do not update the Console.

### Dataset preparation progress

Before preparing a dataset, call `inspect_dataset_workbench` and resume its
`preparation_workflow`, or call `start_dataset_preparation` with a stable request key.
Keep it preparing across local authoring, previews and publications. Call
`update_dataset_preparation` with `state="completed"` and verified published output
cell UUIDs only when all requested agent work is finished. Use `paused` when stopping
temporarily or `cancelled` when abandoning the workflow. Individual job completion
does not finish preparation.

The Console keeps one evolving notification for the workflow; upload, import and
pipeline events remain recorded beneath it. No page refresh is required. Pausing
is an explicit report, not inferred from a disconnected client.
